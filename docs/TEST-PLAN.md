## Affected Pages/Routes
- CLI: `btc-vault demo theft-refused` — the v0 acceptance flow: fund regtest vault, honest spend confirms (through the Hold, time-warped), act one: theft refused by all nodes with structured reason, act two: allowlisted theft caught mid-Hold and clawed back by escape sweep; meaningful exit code. (Milestones per design doc: v0 = the full core incl. Hold/PINs/duress/watchtower — the former v0.1/v0.2 split is retired; v1 = deployer/sealing/backend enforcement.)
- HTTP: `POST /sign` (two-phase: `{psbt, escape_psbt, pin}` → pending | signed | refusal) and `GET /events?since=` (alerts, pending spends, sign-log, liveness) on each vault-node; all adversarial input lands here.

## Key Interactions to Verify
- Honest spend end-to-end on regtest: build hot tx + escape variant → user signs both → PIN → fan out to 5 nodes → all pending → re-submit after Hold → collect 3-of-5 → finalize → broadcast → confirm.
- Hold semantics: hot-class pending at first submission; re-submission before D → still pending; after D → signed; escape and refresh classes sign instantly with no pending phase.
- Duress: duress PIN → wire response byte-identical to normal pending; configured duress_response executes (escape broadcast and/or lockdown); lockdown persists across node restart; all subsequent submissions → FRAUD_SUSPECTED.
- Escape-sweep cancel: escape sweep confirms → conflicting pending spend can never complete (inputs gone); node prunes it.
- PIN gate: missing/wrong PIN → BAD_PIN, nothing signed, ever.
- Log reconciliation: a sign event pulled from a node that the coordinator didn't originate → user-facing alert.
- Watchtower: recovery-path spend on regtest → every node queues an alert; vault spend a node never co-signed → alert; GET /events cursor loses nothing, duplicates nothing.
- Theft attempt (attacker holds user key, non-allowlisted destination): every node refuses; refusal reason names the failing check.
- Mixed outcome: quorum reached with one refusal → transaction broadcasts AND a structured alert is emitted naming the refusing node and reason (decided D7/4A).
- Node availability: 2 nodes down on 3-of-5 → spend still succeeds; 3 nodes down → clean failure with a clear insufficient-quorum message, no hang.
- Demo idempotency: re-running `btc-vault demo` on dirty state (existing containers/wallet) either cleans up or fails with a clear message — never a half-broken federation.
- Setup validation: vault setup without an escape-cold-wallet allowlist entry fails with a clear message (mandatory per Wallet Topology); duress PIN equal or typo-adjacent to normal PIN → rejected at enrollment; escape descriptor sharing a BIP32 fingerprint/xpub/pubkey with the user key → hard error (ADR-0003 tripwire).

## Edge Cases
- Change output labeled as change but NOT derivable from the vault descriptor → refused (theft vector; policy-core unit test, both branches).
- Every policy check, pass AND fail branch (definitions in the design doc's Policy model section): allowlist (descriptor-derived at bounded index, scriptPubKey equality; OP_RETURN refused; allowlisted wallet's address beyond max_derivation_index refused), fee ≤ max_fee_pct × Σinputs (at/over/under boundary, all classes incl. escape), input ownership (untrusted-hint re-derivation, bounded scan), sighash enforcement (user sig verified against recomputed sighash; non-ALL sighash refused — subsumes output-mutation), PSBT global/input/output consistency.
- Anti-replay (v0.2 semantics): identical commitment resubmitted within expiry → recorded verdict returned (idempotent); expired commitment → COMMITMENT_EXPIRED refusal; coordinator-proposed expiry beyond node's max_commitment_age_secs → refused; RBF replacement (new commitment, same outpoints) → evaluated fresh, NOT blocked by the log.
- Malformed PSBT to `/sign` → 400 with structured error, no panic.
- PSBT missing or carrying an invalid user signature → refusal (never a node signature on a user-unsigned tx).
- PSBT for a different descriptor than the node's configured vault → refusal.
- Property tests (proptest): no mutated transaction passes an authorization bound to the original.

## Critical Paths
- `btc-vault demo theft-refused` exits successfully from a clean clone with one command (v0.1 success criterion).
- policy-core evaluation is deterministic and pure: same PSBT + policy → same verdict on every node (federation consistency depends on it).
- The seven v1 attack scenarios (stolen-user-key, compromised-node, mutation, replay, stolen-recovery-keys, compromised-quorum, recovery-drill) each run reproducibly and report honest pass/fail — including the two the vault deliberately loses.
