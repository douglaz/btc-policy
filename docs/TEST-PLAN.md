# Test Plan

> **SUPERSEDED IN PART (2026-07-15).** This plan predates Model B. It is authoritative only where it does not conflict with [ADR-0012](adr/0012-model-b-spend-and-duress-architecture.md) (architecture + duress), [ADR-0013](adr/0013-concrete-protocol-schemas.md) (concrete schemas), and [V0-PLAN.md](V0-PLAN.md) — **those win on every conflict.** The body below is left as-is; these items are known-superseded:
> - **Assembly + broadcast:** the coordinator-assembles-and-broadcasts flow is retired — under **Model B the nodes assemble partials over the Node channel and each broadcasts**; the coordinator is a pure relay that never combines, finalizes, or broadcasts (ADR-0012).
> - **`/sign` contract:** the `{psbt, escape_psbt, pin}` body is replaced by the **coordinator-signed tagged request schema** — `SpendRequest{spend, escape, pin, nonce, expiry, policy_version}` plus a pin-less `RefreshRequest`, escape mandatory, coord-signed and fresh (ADR-0013 §2).
> - **Watchtower criterion:** "a vault spend a node never **co-signed** → alert" is the wrong test (it false-alarms on the n−t legitimate non-signers) — the criterion is now "never **validated** (saw and policy-checked the request)" (ADR-0012).
> - **Retired milestones:** the v0.1 / v0.2 milestone split (and the "v0.2 semantics" anti-replay framing) is retired — v0 is the full core; see V0-PLAN.md.
> - **Attack scenarios (2026-07-21):** the seven-scenario v1 set under *Critical Paths* (stolen-user-key, compromised-node, mutation, replay, stolen-recovery-keys, compromised-quorum, recovery-drill) is retired. It predates the two-track duress state machine and framed safety as a receipt count; the 2026-07-20 dual-model review settled the property on the **coupling + release-gate** instead (ADR-0012). It is replaced by the adversarial regtest harness described below.

## Affected Pages/Routes
- CLI: `btc-vault demo theft-refused` — the v0 acceptance flow: fund regtest vault, honest spend confirms (through the Hold, time-warped), act one: theft refused by all nodes with structured reason, act two: allowlisted theft caught mid-Hold and clawed back by escape sweep; meaningful exit code. (Milestones per design doc: v0 = the full core incl. Hold/PINs/duress/watchtower — the former v0.1/v0.2 split is retired; v1 = deployer/sealing/backend enforcement.)
- HTTP: `POST /sign` (two-phase: `{psbt, escape_psbt, pin}` → pending | signed | refusal), `GET /events?since=` (alerts, pending spends, sign-log, liveness), `POST /channel` (authenticated node-to-node envelopes, channel mode only), `GET /healthz` (read-only liveness: `{serving, locked_down, last_deadline_tick, generation_claimed}`, pin-uniform), and `GET /pending` (read-only accepted-but-unsettled spend projection: `{pending: [commitment_id, ...]}`, pin-uniform) on each vault-node; all adversarial input lands here, `/healthz` and `/pending` included — both are reachable over the same coordinator relay path.

## Key Interactions to Verify
- Honest spend end-to-end on regtest: build hot tx + escape variant → user signs both → PIN → fan out to 5 nodes → all pending → re-submit after Hold → collect 3-of-5 → finalize → broadcast → confirm.
- Hold semantics: hot-class pending at first submission; re-submission before D → still pending; after D → signed; escape and refresh classes sign instantly with no pending phase.
- Duress: duress PIN → wire response byte-identical to normal pending; configured duress_response executes (escape broadcast and/or lockdown); lockdown holds for the node's lifetime, and a rebooted node is DEAD — bare machine requiring full re-provisioning, never a node that comes back locked-down (RAMDISK deployment, ADR-0007; reboot-death/tmpfs, 2026-07-16); all subsequent submissions → FRAUD_SUSPECTED.
- Escape-sweep cancel: escape sweep confirms → conflicting pending spend can never complete (inputs gone); node prunes it.
- PIN gate: missing/wrong PIN → BAD_PIN, nothing signed, ever.
- Log reconciliation: a sign event pulled from a node that the coordinator didn't originate → user-facing alert.
- Watchtower: recovery-path spend on regtest → every node queues an alert; vault spend a node never co-signed → alert; GET /events cursor loses nothing, duplicates nothing.
- Theft attempt (attacker holds user key, non-allowlisted destination): every node refuses; refusal reason names the failing check.
- Mixed outcome: quorum reached with one refusal → transaction broadcasts AND a structured alert is emitted naming the refusing node and reason (decided D7/4A).
- Node availability: 2 nodes down on 3-of-5 → spend still succeeds; 3 nodes down → clean failure with a clear insufficient-quorum message, no hang.
- Demo idempotency: re-running `btc-vault demo` on dirty state (existing containers/wallet) either cleans up or fails with a clear message — never a half-broken federation.
- Setup validation: vault setup without an escape-cold-wallet allowlist entry fails with a clear message (mandatory per Wallet Topology); duress PIN equal or typo-adjacent to normal PIN → rejected at enrollment; escape descriptor sharing a BIP32 fingerprint/xpub/pubkey with the user key → hard error (ADR-0003 tripwire). **Extended 2026-07-25 (bead btc-policy-9y5.5), now that the ceremony is real (`btc-vault setup`, `docs/SETUP-CEREMONY.md`):** the escape wallet's DERIVED keys are scanned over `0..=max_derivation_index` against the user key, every node key, and every recovery key, and any overlap is a ceremony REFUSAL — the check with teeth now that vault keys are definite and carry no origin to compare. Covered by `setup::tests` (`a_shared_seed_escape_is_refused_at_ceremony_time`, `an_escape_sharing_a_node_or_recovery_key_is_refused`, `an_escape_sharing_an_origin_with_the_hot_wallet_is_refused`). Also ceremony-refused there rather than at node startup: a federation shape other than `n = 2t − 1`, a ranged vault key, a non-loopback v0 endpoint, and an endorsement that does not verify.

## Edge Cases
- Change output labeled as change but NOT derivable from the vault descriptor → refused (theft vector; policy-core unit test, both branches).
- Every policy check, pass AND fail branch (definitions in the design doc's Policy model section): allowlist (descriptor-derived at bounded index, scriptPubKey equality; OP_RETURN refused; allowlisted wallet's address beyond max_derivation_index refused), fee ≤ max_fee_pct × Σinputs (at/over/under boundary, all classes incl. escape), input ownership (untrusted-hint re-derivation, bounded scan), sighash enforcement (user sig verified against recomputed sighash; non-ALL sighash refused — subsumes output-mutation), PSBT global/input/output consistency.
- Anti-replay (v0.2 semantics): identical commitment resubmitted within expiry → recorded verdict returned (idempotent); expired commitment → COMMITMENT_EXPIRED refusal; coordinator-proposed expiry beyond node's max_commitment_age_secs → refused; RBF replacement (new commitment, same outpoints) → evaluated fresh, NOT blocked by the log.
- Malformed PSBT to `/sign` → 400 with structured error, no panic.
- PSBT missing or carrying an invalid user signature → refusal (never a node signature on a user-unsigned tx).
- PSBT for a different descriptor than the node's configured vault → refusal.
- Property tests (proptest): no mutated transaction passes an authorization bound to the original. Built in V0-7; three suites, all `dev-dependencies` only:
  - `crates/vault-node/src/prop_mutation.rs` — structural PSBT mutations (input/output insert, drop, value, scriptPubKey, `nSequence`, `nLockTime`, `nVersion`, prevout, witness bytes) on a user-signed spend AND its paired escape, driven through the real `/sign` ingress: every consensus-relevant mutation changes the `commitment_id`; a mutant carried on the original's `coord_sig` is `COORD_AUTH_INVALID`; a mutant the coordinator *re-signs* is still refused, because the user's signature no longer covers the transaction.
  - `crates/vault-proto/tests/prop_commitment_binding.rs` — the same invariant at the encodings: the commitment's canonical encoding is injective (including input/output ORDER), and a coordinator signature never transfers to a different request or a different `wallet_id`.
  - `crates/policy-core/tests/prop_refusal_core.rs` — arbitrary output sets against a fixed vault/escape/hot descriptor set, checked against a complete refusal oracle: unrecognized output ⇒ refused, mixed hot+escape ⇒ `PSBT_INCONSISTENT`, an attacker-controlled output is only ever `Hot` or refused (never `Escape`/`Refresh`), `hot_outflow` is the non-vault/non-escape sum, and the per-tx Hot cap refuses exactly when outflow exceeds it.
- Decoder robustness (proptest in place of cargo-fuzz, which needs a clang/LLVM toolchain this build environment does not have): arbitrary bytes, near-valid bodies (one field replaced, one byte flipped, truncated), and *authenticated* garbage (a correctly channel-signed envelope or correctly coord-signed request whose payload is noise) at every untrusted-input parser — `crates/vault-node/src/prop_decoder.rs` for the `/channel` envelope verify/decode path and the `/sign` ingress, `crates/vault-proto/tests/prop_decoder_robustness.rs` for the wire DTOs. No input panics; malformed input is a typed refusal; the near-valid corpus asserts the EXACT reject reason so a check that stopped firing cannot hide behind "it was rejected anyway".

## Critical Paths
- `btc-vault demo theft-refused` exits successfully from a clean clone with one command (v0.1 success criterion).
- policy-core evaluation is deterministic and pure: same PSBT + policy → same verdict on every node (federation consistency depends on it).
- ~~The seven v1 attack scenarios (stolen-user-key, compromised-node, mutation, replay, stolen-recovery-keys, compromised-quorum, recovery-drill)~~ — **superseded 2026-07-21**, see the banner. The launch-gate set is now `btc-vault attack [scenario|all]`, a live-regtest adversarial harness over a co-located `n = 2t−1` federation with a real compromised minority (`crates/vault-cli/src/attack.rs`). It exits 0 only when every safety assertion holds, and prints a scorecard row per scenario:

  | scenario | what it demonstrates |
  | --- | --- |
  | `arm-split-closed` | the **coupling**: a coordinator splitting the carrier from the signature via each ADR-0012 vector (corrupt escape, oversize past `max_msg_bytes`, lapsing expiry) still leaves ≤ `t−1` releasable partials |
  | `censorship-residual-bounded` | the **Hot budget** (ADR-0014): over-cap refused pre-signing at every node, window sum capped, unexposed reservations returned |
  | `selective-delivery` | one coordinator delivery fans out to every live honest node; the coupling, not an armed-node count, keeps coerced partials frozen, with `wiretap_positive_control` supplying the per-node release-path control and the sweep a second one for the escape-role decoder |
  | `two-spend-probe` | **silence**: identical body, size, and `/events` under both pins, including the Hot-budget refusal path; wall-clock skew is measured and reported as advisory because CI variance exceeds the one-Argon2 effect it was meant to detect. The hard ingress-work gate is deterministic: `normal_and_duress_ingress_op_sequences_*` compares each pin's `/sign` acknowledgement field-for-field, its ordered handler ops, a canonical pin-masked projection of the whole channel store, a projection of the whole `/sign` handler state (replay, pending, coordinator-nonce and refresh logs plus the PIN attempt budget), the channel schedule-work delta, PIN evaluations, and carrier derivations across first-carrier, armed, fresh and replay-cached escape-class, replay-cached Hot, Hot-budget-refusal, and LOCKED-OUT shapes — the last being the attacker's cheapest probe (flood wrong pins, then submit a valid one) and the path where §0's fail-closed rule makes a refused duress request still derive its carrier, run the arm hook, and stage for peers. The two projections are read off fields rather than hand-placed instrumentation, so a duress-only NET state difference anywhere in the channel store or in `SignState` — the latter being where the pin verdict itself is written, via `AttemptBudget::charge` — is covered generically; the vault-authorized set, the peer OUTBOX and the remaining handler locals have only the ordered log's instrumented call-site coverage, as does a write reverted within the same pass (the Hot-budget reserve/unwind pair, which is instrumented for exactly that reason). For the outbox that is `OutboxPush`'s presence and position, never its CONTENTS — the staged request carries the coordinator's bytes with the pin in them, so it differs by pin by construction and would need masking like a carrier id. The capture ends when the synchronous handler returns: the server's subsequent outbox drain and spawned peer sends are exercised by live propagation scenarios but are outside this deterministic record, so it is not an end-to-end timing gate. The `/healthz` and `/pending` duress-oracle properties — byte-identical projection armed-pre-`T` vs idle, and byte-identical under both pins — are proven separately by `healthz_is_byte_identical_on_an_armed_pre_t_node`, `pending_is_byte_identical_on_an_armed_pre_t_node`, and `pending_is_byte_identical_under_the_normal_and_duress_pins`; `demo theft-refused` covers `/pending` end-to-end on the path that matters by requiring every node to name the attacker's accepted candidate. |
  | `toxic-parent` | an escape over a replaced external parent never releases a share; Lockdown at T regardless |
  | `in-flight-refresh` | the escape chains off the refresh output; coarse subordination; coerced spend dead |
  | `escape-class-sequences` | the two-slot record and `Idle→Armed` suppression; the normal pin's delayed slot is a no-op |
  | `hold-expiry-race`, `lockout-then-duress`, `duress-resubmission` | arming against a pending, locked-out, or already-registered commitment |
  | `reboot-death` | a killed node cannot restart or rejoin (ADR-0007); above `t` still sweeps, below `t` is lockdown-only |
  | `fire-time-failure` | coverage / feerate / package refusals stop the sweep but never the unconditional Lockdown |
  | `recovery` | the demonstrated exit from the lockdown-only branch: V0-10 timelocked recovery spend confirms |

  Each scenario asserts no theft path, the safety track (freeze + unconditional Lockdown at T), and — where it argues from an ABSENT partial — pairs that absence with a positive control in the same federation, so a deaf wiretap cannot pass vacuously. Two controls do different jobs and neither substitutes for the other. The scenario's own escape sweep is a DECODER control: it shows the listener parses an escape-role envelope, and it is deliberately taken *after* the absence read, so the same decode path is live at a later instant than the zero was read at. But one observed sender cannot license a claim that ranges over every honest node — a single node's silently broken fan-out reads exactly like that node's freeze holding — so any scenario whose headline claim is per-node also runs `wiretap_positive_control` first, while the federation is whole, which requires a validated share from *every* honest daemon. The one exception is `in-flight-refresh`, where a completed control spend keeps a candidate registered and subordinates the very refresh under test (`REFRESH_SUBORDINATED`); it carries the decoder control only, and says so at the call site. Wrapped for CI-style invocation by the `#[ignore]`d launch-gate test in `crates/vault-cli/tests/e2e.rs`, and **run on every push** by the `launch-gate` job in `.github/workflows/ci.yml` — `attack all` plus both demos, with the resolved toolchain, binary hashes, effective config, and scorecard uploaded as artifacts. That job is the reason "every scenario holds" is a standing property rather than a manual claim; an unenforced gate rots, and for custody code it rots silently. `btc-vault demo first-light` remains the one-command smoke path, and `btc-vault demo theft-refused` is the named v0 acceptance artifact.
