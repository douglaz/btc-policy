## Problem Statement

Bitcoin self-custody has no good answer to "what happens when my key is stolen" short of covenants that aren't activated. Existing options either trust a single company's off-chain policy (Swan Vault's 72-hour hold), trust a single self-hosted policy server (IDEA.md's original 2-of-2 design — one host compromise away from useless), or accept Revault-grade operational complexity. IDEA.md §5.2 identifies the core flaw in conventional 2-of-3 "policy multisig": any two user keys can bypass the policy key entirely.

This project builds a **federation of policy enforcers**: t-of-n signer nodes, each holding one multisig key *and* one policy engine, each independently refusing to sign any PSBT that violates the shared policy. The user's hardware key is mandatory alongside the federation quorum, so nodes can never spend without the user, and a stolen user key alone is refused by every honest node. Policy enforcement stops being a single point of failure and becomes majority-enforced: an attacker must compromise the user key AND t independently-hosted nodes.

On-chain shape — sketched in rust-miniscript's concrete **policy language** (the sketch below is *not* itself Miniscript; vault-cli compiles it into a Miniscript descriptor at vault creation **[SUPERSEDED by [ADR-0013](adr/0013-concrete-protocol-schemas.md) §1 — the descriptor is a FIXED, HAND-WRITTEN template with keys substituted at setup, NOT compiled from policy at runtime; rust-miniscript is authoritative for parsing/satisfaction/branch-recognition but is NOT used as a runtime policy compiler. This resolves the contradiction with "the descriptor is hand-written" stated later in this doc]**; mainnet-deployable today):

```
or(
    and( pk(user_hw), thresh(t, node_1 ... node_n) ),
    and( older(~180 days), thresh(2, rec_a, rec_b, rec_c) )  # [was "~90 days" — SUPERSEDED by ADR-0013 §1: locked default is 180d = BIP68 30375 (512-sec units); distinct from and must stay >> the ~90-day refresh cadence]
)
```

The timelocked recovery path backstops federation loss or a lost user key.

**Terminology — "policy" does three different jobs in this project; keep them apart:**

1. **Spending policy (on-chain)**: the policy-language expression above, compiled into the vault's Miniscript descriptor and enforced by Bitcoin consensus. This is what rust-miniscript's `policy` module refers to.
2. **Policy checks (off-chain)**: the PSBT checks every vault-node runs before contributing a signature — what the `policy-core` crate implements. Unrelated to rust-miniscript's `policy` module despite the name.
3. **Policy config**: the per-node file that parameterizes the checks (allowlist, fee cap, expiry cap). See "Policy model" below.

## What Makes This Cool

- **The demo**: `btc-vault demo theft-refused` — act one: an attacker holding the user's key builds a sweep to an unknown address, and the federation refuses it with a structured, legible reason. Act two: the attacker's *allowlisted* spend is caught mid-Hold as a pending spend the user never made, and clawed back by an instant escape sweep. Later (`btc-vault attack [all|<scenario>]`), a whole adversarial playbook runs against a live federation on the user's own VPSes.
- **Every quorum has run the checks by construction.** Unlike 2-of-3-with-a-policy-key, there is no signature path that bypasses policy — the elegance that made the federation reframe land.
- **The deployer is the product.** `vault deploy --hosts a,b,c` makes correct topology the default instead of a security footnote — including *provider* diversity: the deployer warns when a quorum majority lands on a single hosting provider, since co-located nodes are correlated compromises. Target experience: "a few cheap VPSes and my laptop, and 15 minutes later I had a 3-of-5 vault that refused to sign a theft."
- **Empty niche.** No standalone Rust PSBT policy-evaluation crate exists (July 2026 landscape check); Keep bundles policy inside experimental FROST; Revault targets orgs. (Covenants/CTV are explicitly out of scope — this is a soft vault on today's consensus rules.)

## Constraints

- Rust throughout; mainnet-compatible under current consensus rules (no covenant dependency).
- Open source, self-hostable; audience is self-custody power users ("can I run it on my boxes?" is the acceptance test).
- **Simplicity and control over dependencies**: every dependency must beat the cost of writing it. Core deps: BDK + rust-miniscript (+ Liana's policy compiler only if it earns its keep). walletrs is reference material, not a foundation.
- Soft-vault honesty: t compromised nodes + user key = theft. The project states this openly (and demos it — the `compromised-quorum` scenario succeeds on purpose).
- Solo builder, CC-assisted; momentum matters — never more than ~a week from a runnable end-to-end loop.

## Premises

1. **Federation, not co-signer** — the vault is a user hardware key AND a t-of-n quorum (e.g., 3-of-5) of signer nodes; every node independently validates the exact PSBT against the shared policy before contributing a signature. Theft requires the user key plus t compromised nodes. Timelocked recovery backstops loss. Accepted limit: this is a soft vault, not a covenant vault.
2. **Federation runtime is the goal, crate is the foundation** — the deliverable is the node daemon (key + policy engine + coordination) plus the CLI that deploys and runs federations; the signer-agnostic PSBT policy crate is the load-bearing core each node embeds, not the end product.
3. **Lean dependency core** (revised after cross-model challenge) — BDK + rust-miniscript are the hard dependencies; Liana's descriptor/timelock pattern is the design reference for recovery; walletrs is demoted to optional reference/coordinator. Guiding rule: keep things simple and under our control; each dependency is weighed against the simplicity cost.
4. **Distribution in scope for v1** — prebuilt binaries + container images via GitHub Releases with CI (GitHub Actions); multi-VPS provisioning ships inside the CLI (SSH-based), not as separate Ansible/Terraform artifacts.

## Approaches Considered

### Approach A: Minimal Federation (regtest, one command)
One Rust workspace — `policy-core` crate, `vault-node` daemon, `vault-cli`. The CLI launches 5 local nodes (3-of-5) + regtest bitcoind, funds the vault descriptor, runs one honest spend and one theft attempt that the nodes refuse. No SSH, no VPS, no watchtower yet.
Effort: S–M (CC-assisted: ~1–2 weeks of sessions). Risk: Low.
Pros: end-to-end federation demoable in days; every line survives into later phases; forces the authorization/refusal protocol design early where changes are cheap.
Cons: localhost hides ops reality (TLS, provisioning, latency, restarts); no recovery path or watchtower in v0.
Reuses: BDK (wallet/PSBT), rust-miniscript (descriptor), bitcoind regtest, Keep's signer policy fields as prior art.

### Approach B: The Attack Range (full deployer + scenario playbooks)
"Metasploitable for Bitcoin vaults": `vault deploy` provisions nodes over SSH onto real VPSes (signet), `vault attack --scenario {stolen-user-key, compromised-node, replay, mutation, stolen-recovery-keys, compromised-quorum, recovery-drill}` runs reproducible adversarial playbooks with honest pass/fail output — including the scenarios the vault loses (compromised quorum; stolen recovery keys after the timelock, unless the watchtower catches the sweep in time).
Effort: XL (CC-assisted: ~2–3 months of sessions). Risk: Medium — ops surface can swallow the novel work.
Pros: the complete power-user artifact (their boxes, real network, provable claims); the scenario scorecard becomes the project's trust currency; deployer makes correct topology the default.
Cons: months before first shareable artifact if built as one piece; provisioning code dominates the diff.
Reuses: everything from A, plus Liana's recovery pattern, container tooling.

### Approach C: Scenario-Driven Federation (attack harness as the spec)
Write the attack scenarios first as an executable acceptance suite; grow the federation to pass them one by one; publish a per-release scorecard. The harness itself is a standalone artifact other custody projects could run.
Effort: M–L (CC-assisted: ~3–5 weeks of sessions). Risk: Medium — harness abstractions designed before the system exists tend to need rework.
Pros: security claims are tests, not prose; second deliverable with independent community value; keeps development honest.
Cons: test infrastructure before the system risks abstracting wrong; slower to the first "theft refused" moment.
Reuses: A's workspace shape; proptest ecosystem; regtest harness patterns from repos/ (simple-ctv-vault's test style).

## Recommended Approach

**A now, B as a fast follow-up** (user decision). Ship the minimal co-located federation first: it gets a real theft-refusing federation running in days and keeps momentum. Approach B — the SSH deployer and attack-scenario playbooks — is Phase 2, not a someday; C's scenario scorecard folds into B as the playbook engine. A's components are real daemons co-located only by deployment choice, so B is growth, not rewrite.

Workspace shape (from Codex's weekend build, adopted; vault-proto added in eng review):

```
btc-vault/
  crates/
    policy-core/    # PSBT policy evaluation + TOCTOU-safe authorization (signer-agnostic, PURE — no wire/serde concerns)
    vault-proto/    # shared protocol vocabulary: tx commitment struct, refusal codes, /sign wire DTOs
    vault-node/     # daemon: one key, one policy engine, POST /sign, structured refusals
    vault-cli/      # coordinator + demo runner (later: SSH deployer + attack scenarios)
```

Both binaries import `vault-proto`, so a commitment-structure or refusal-code drift between coordinator and node is a compile error, not a runtime validation gap (eng review D6).

**`/sign` wire contract** (current v0, defined in `vault-proto`): a coordinator-signed tagged union of `SpendRequest { spend, escape, escape_bumps, pin, nonce, expiry, policy_version }` and the pin-less `RefreshRequest { refresh, nonce, expiry, policy_version }`. The mandatory escape accompanies every SpendRequest, regardless of transaction class; `escape_bumps` is the optional pre-signed fee ladder and its length is always bound into the coordinator-auth preimage, even when it is empty and omitted from the JSON body. A successful ingress returns `200 { accepted: { commitment_id, first_seen, remaining_secs } }`; the nodes retain, exchange, combine, and broadcast their signatures, so no response returns a partial or signed PSBT. A policy outcome returns `200 { refusal: { code, check, detail } }`; only undecodable input is `400`. Normal and duress PINs return the same accepted/refusal shape, while the internal duress intent can arm asynchronously.

The authoritative refusal enum is `vault_proto::RefusalCode`. Its current variants are `WRONG_DESCRIPTOR`, `UNKNOWN_INPUT`, `DEST_NOT_ALLOWED`, `CHANGE_NOT_DERIVABLE`, `FEE_EXCEEDS_CAP`, `BAD_SIGHASH`, `USER_SIG_INVALID`, `COMMITMENT_EXPIRED`, `PSBT_INCONSISTENT`, `BAD_PIN`, `FRAUD_SUSPECTED`, `COORD_AUTH_INVALID`, `NONCE_REPLAYED`, `COORD_NONCE_CAPACITY`, `CANDIDATE_CAPACITY`, `EXPIRY_TOO_SHORT`, `REFRESH_TOO_SOON`, `REFRESH_FEE_EXCEEDS_CAP`, `REFRESH_SUBORDINATED`, `HOT_BUDGET_EXCEEDED`, and `HOT_VELOCITY_EXCEEDED`. The last two are the Hot-budget refusals: per-transaction and rolling-window respectively (`HOT_VELOCITY_EXCEEDED` also answers the ledger's own count cap, which means the same thing to a coordinator — no more hot outflow is metered here until reservations age out — and names the bound that bit in its `detail`). Both occur before signing, and both still stage an otherwise processable duress carrier, so the spend is refused without suppressing the freeze. The two differ in reach: only `HOT_BUDGET_EXCEEDED` can also be raised on a request's paired *escape* (`verify_escape` runs the same pure `evaluate`, so an "escape" that actually pays the hot wallet trips the per-tx cap before the class check names it), where it carries an `escape:` check prefix and stages nothing, like every other escape-derived refusal. `HOT_VELOCITY_EXCEEDED` is spend-only by construction — the ledger meters the spend and never the escape, since an escape sweep consumes no budget. Nodes expose a cursor-based pull API, `GET /events?since=`, for alerts and the sign/refuse log (ADR-0002). **Pending spends and liveness are NOT on `/events`** — an earlier version of this line put all four there, before the surfaces were split: the accepted-candidate projection is `GET /pending` (the incident surface an operator diffs against what they authorized), and liveness is `GET /healthz`, whose contract is documented immediately below.

**`/healthz` wire contract** (v0, `vault_node::Health`): `GET /healthz` returns `200 { serving, locked_down, last_deadline_tick, generation_claimed }` — the node's non-secret liveness state, so an operator can tell a dead, store-wedged, poison-bricked, or locked-down node from a healthy one without probing it with a spend. `serving` is a constant `true`: it says the daemon parsed its config and is answering HTTP, which is exactly what the `200` says and no more — it is not an identity claim, since any process on the port can emit the same byte. `locked_down` is the terminal Lockdown latch; `last_deadline_tick` is the SAFETY deadline driver's heartbeat, a wall-clock second bucketed to `DEADLINE_HEARTBEAT_RESOLUTION_SECS` and `null` before that driver's first pass; `generation_claimed` is the one-shot process-generation marker (ADR-0007). The production `serve` boundary claims the generation before accepting HTTP, so a production daemon that is serving reports `true`; `false` is meaningful to direct router embedders and tests. Two of the four fields are therefore constants on a live production daemon, and the projection an operator actually reads is `locked_down` plus the heartbeat.

**What the heartbeat covers, and what it does not.** `last_deadline_tick` is published by the Lockdown deadline driver alone — not by `fire_tick`, the watchtower scan, or the vault-scan cache refresher. It goes stale on a dead process, a runtime that has stopped scheduling, a channel store lock held or wedged (the next deadline pass blocks in `lockdown_due`), and the poison-bricked node (passes stop once a critical lock is poisoned and the fail-closed latch has fired, so a stale heartbeat beside `locked_down: true` names that state). It does NOT go stale when a release/combine/broadcast pass, the watchtower, or the cache refresher is stuck in a chain-backend RPC: all three reset their ticker from pass completion, so each one's phase is a function of its last pass's duration — and the fire pass's duration depends on what the candidate registry holds, i.e. on whether the node is ARMED. Publishing that phase would give a polling coordinator the pre-`T` arm signal SILENCE denies it; bucketing a timestamp coarsens a secret-dependent cadence, it does not remove it. Pin-uniformity beats coverage wherever the two collide, and the residual blind spot is stated rather than papered over: a backend call that FAILS prints on the node's own log, a call that BLOCKS forever prints nothing, and `/events` never carried sweep progress at all (its queue takes watchtower alerts and channel freshness rejects only). A backend-wedged sweep is invisible from outside a v0 node — the field that would show it is the arm-dependent one SILENCE forbids. The endpoint is read-only, `GET`-only, and takes no node lock, so it answers promptly while `sign_state` or the channel store is held — the contention an operator probing a stuck node is trying to see through. The production Tokio runtime keeps at least three worker threads — `available_parallelism()` where the host has more — so that even on a one- or two-vCPU host the deadline and fire-driver prologues can each pin one while waiting on a wedged store and a third still polls the listener and this lock-free handler.

It is reachable on the same coordinator relay path as `/sign`, and the coordinator is hostile-at-wrench (ADR-0010/0012), so **every field is PIN-UNIFORM**. `locked_down` is public terminal state and already externally observable (the node refuses every spend); its normal transition is post-`T`, while persisted-latch adoption and critical-lock poison recovery may engage it earlier only on pin- and arm-independent fail-closed paths. `last_deadline_tick` is published by the never-reset, backend-independent deadline-driver ticker rather than by the completion-scheduled release/combine pass, whose duration can differ after arming; timestamp bucketing is not used to conceal that secret-dependent cadence. That separation is not a categorical scheduler-isolation claim: each deadline iteration synchronously reads the channel store, the fire pass uses the same mutex, and contention can therefore postpone the next deadline iteration and its bucket publication even though the fire pass never writes the field. There is deliberately no arm state, pending/candidate count, `T`, hold/fire deadline, or per-commitment field: an **ARMED-but-pre-`T`** signal is a duress oracle a coordinator could simply poll, and the rule for extending the projection is the one that kept those out — if a pre-`T` duress carrier can change a field, the field does not belong there. The load-bearing property — that the whole wire projection is byte-identical whether or not a node is armed pre-`T` — is proven deterministically by the `healthz_is_byte_identical_on_an_armed_pre_t_node` unit test: it arms one node and an idle twin from the SAME config, runs one absolute-schedule deadline pass on each at the same instant so the heartbeat is part of the compared bytes, and asserts the projections are equal under a paused clock — so the guarantee rests on a test no scheduler timing can flake, not on threading `/healthz` polling through the attack harness's tight pre-`T` hostage window (which only fought that window and proved nothing the unit test does not). The only residual is end-to-end *latency* on any surface of the host: it reflects what else that host is doing, and the release/combine pass does arm-dependent work. That channel belongs to co-residency — equally present on `/events` and on the TCP accept, not created or widened by a handler that reads three atomics and takes no lock — and has no wall-clock signal with enough power over host variance to serve as a correctness gate, so it is a documented co-residency residual, not a `/healthz` field.

**`/pending` wire contract** (v0, `vault_node::PendingProjection`, bead btc-policy-k0t): `GET /pending` returns `200 { pending: [commitment_id, ...] }` — the sorted commitment ids of the spends this node has ACCEPTED and has not yet seen settle. One snapshot is served at a time; a concurrent read is shed with `429` (and a poisoned-lock unwind answers `500`), so a poller must distinguish both from an empty projection rather than reading either as "nothing pending". It exists to close a threat-model gap the theft demo used to disclose as a printed caveat. The MODELLED attacker (stolen user key + PIN, but not the coordinator auth key) has to relay through the user's OWN coordinator, so the `/sign` acknowledgements surface the theft; a strictly stronger thief who ALSO holds the coordinator auth key can feed ONE node directly and let §3 request propagation reach the rest, and before this route no surface the user watches would have shown it — `GET /events` carries on-chain watchtower alerts only, and no node answered "what have you accepted?". During the Hold, every node now names the candidate, so noticing the theft no longer depends on the relay. Read-only and `GET`-only: it is a projection, not a control plane, and adds no way to cancel, accelerate, or influence a candidate.

**Why it is not a duress oracle, and what it costs.** It is a function of the `PendingLog` (`commitment_id -> expiry`) ALONE, so the handler never reads the channel store — where every piece of duress state lives (arm intents, `T`, Armed-vs-Scheduled, the sweep and its ladder). That is structural, not a claim about which fields were picked, and it is what the `pending_answers_while_the_channel_store_is_held` test observes from outside. The log has three writers and the pin class reaches none of them: **record** at ingress is gated on `class == Hot` and nothing else, so a duress-pin and a normal-pin spend of the same transaction record the same id under the same expiry; **remove** happens only once a candidate is observed on the network (including a conflicting escape-class implicit cancel), a public event; **prune** runs on the coordinator's own `expiry`. So a duress-carrying node's projection can differ from an equivalent normal-pin node's only AFTER a transaction the whole world can already see has settled — and dynamic-`T` corroborates it from the other side, since `T <= earliest pending hot Hold-expiry - epsilon_secs` puts the PUBLIC Lockdown strictly before the frozen spend could have settled on the normal path. The byte-identical property is proven deterministically by two unit tests, `pending_is_byte_identical_under_the_normal_and_duress_pins` (same request, same node config, only the PIN differs) and `pending_is_byte_identical_on_an_armed_pre_t_node` (an idle twin against a node armed through the production confirmation path, pre-`T`); both compare the COMPLETE body, since a leak would most plausibly arrive as a field nobody thought to name or as a same-width substitution. Deliberately absent, on `/healthz`'s rule plus a second one — every byte here is also visible to the thief, so expose only what closes the gap: no fire time, `T`, Hold remainder or deadline field (the fire schedule is exactly what arming rewrites), no arm state, no txid, PSBT, sighash, partial signature, amount, destination or fee, no escape/ladder/rung, no timestamp, and not even `expiry`, which would have been pin-uniform and safe but closes nothing the id does not already close. Against the modelled attacker this is strictly less than they already hold for their OWN candidates — `/sign`'s `Accepted` carries this same `commitment_id` plus `first_seen` and `remaining_secs` — and the genuinely new increment is that a coordinator-auth-key thief who is not the running coordinator can see that the USER has a spend in flight: an opaque SHA-256 id with no explicit amount, destination or deadline in the body, for a transaction that broadcasts publicly at the end of its Hold anyway. Repeated polling can still bound when an id appears and when it disappears through settlement or expiry; that timing is pin-uniform, but observable. **Lockdown behaviour is deliberate**: a locked-down node answers this exactly like any other node — same route, same shape, no branch. Lockdown is already public (`/healthz`'s `locked_down`, and `FRAUD_SUSPECTED` on every spend), so a Lockdown-shaped branch would add a duress-correlated code path while disclosing nothing new, and emptying or refusing post-`T` would delete precisely the evidence the endpoint exists to provide, at the moment the user most needs it. Unlike `/healthz` this route DOES take `sign_state`, for one `HashMap` scan with no I/O under the guard and no mutation at all, on `spawn_blocking`; one in-flight snapshot is permitted and concurrent polls are shed before they can occupy more blocking-pool workers, with the permit held by the detached job rather than by the handler future so a poller that connects and drops cannot queue past the bound. That is also why the pending count stayed OFF `/healthz`, which keeps its lock-free contract and its liveness-only field set. **The timing half, stated rather than implied**: both tests above compare response BYTES, and this is the one read surface with a handler-side lock wait, so its wall-clock answer does reflect contention on `sign_state`. Every holder of that lock does pin-uniform work in the pre-`T` window — and since bead btc-policy-9zs `/sign`'s critical sections do not run the memory-hard PIN evaluations *at all*: both Argon2id evaluations and the carrier derivation happen in an out-of-lock window between the INGRESS and COMMIT holds, so the work that remains under the lock is pin-uniform with ~600 ms less of it, deterministically gated by the `normal_and_duress_ingress_op_sequences_*` tests plus the structural placement proof `both_memory_hard_operations_run_outside_the_sign_state_lock`; `two-spend-probe` still measures the live wall-clock distribution but reports it as advisory because CI noise exceeds the effect it was meant to detect. Settlement bookkeeping is a write for an event already public on-chain. **The arm-dependent release/combine pass, however, also holds `sign_state`** (`release_guard`, the fail-closed ordering bead btc-policy-9y5.2 pins), so this handler is NOT isolated from it by lock choice, and it would be wrong to claim otherwise: `pending_answers_while_the_channel_store_is_held` shows only that the handler never takes the CHANNEL store, which is a narrower statement. The pin-uniformity of the timing channel rests instead on dynamic-`T`: with `T <= earliest pending hot Hold-expiry - epsilon_secs`, the due set is empty pre-`T` on an armed node and an idle twin alike, so the guarded section does no arm-dependent work on either; after `T`, Lockdown is already public. Two residuals remain, stated rather than implied: the co-residency one documented for `/healthz` (an armed host does arm-dependent CPU work and any observation of that host can be scheduled behind it), and — specific to this route — an unauthenticated poller can observe that `sign_state` was busy, including for a spend that was REFUSED and never appears in the projection. That second one is a spend-activity timing channel available to any network peer, not a duress oracle and not co-residency.

### Policy model

A node's policy is a **closed, hardcoded set of checks** parameterized by a per-node config file — not a rule engine, not a DSL. Adding a check type means shipping code. This is deliberate: an extensible engine is exactly the complexity the dependency-discipline constraint forbids until a real need shows up.

Per-node policy config (TOML, written once at deploy time; **policy is immutable after setup — permanently**. There is no update mechanism at any version; dynamic policy is a declared non-goal. Changing policy means provisioning a new vault and moving funds to it via the normal spend path):

```toml
policy_version = 1               # identifies the baked-at-setup policy; included in every commitment (policy never changes)
descriptor = "wsh(...)"          # the node's OWN copy of the vault descriptor
# The fee guard is fixed in code at 10% for all classes (ADR-0006), not configurable.
hold_secs = 86400                # hot spends wait; escape sweeps and refresh self-spends are instant (ADR-0004)
max_commitment_age_secs = 172800 # node-enforced cap on coordinator-proposed expiry (must exceed hold_secs)
max_derivation_index = 10000     # bound on own-descriptor derivation scans
```

**Check set** (each check ships with pass AND fail tests — eng review D8):

| Check | Definition | Gate |
|---|---|---|
| Input ownership | Every input's prevout scriptPubKey re-derives from the node's **own** descriptor at some index ≤ `max_derivation_index`. PSBT bip32 paths are untrusted *hints* only: the node always re-derives and compares; a hint that doesn't verify is a refusal, and a missing hint triggers a bounded scan. This is also how "the expected wallet descriptor" is matched — a PSBT doesn't declare its descriptor, so ownership of every input *is* the descriptor check. | v0 |
| Destination allowlist | Every output either (a) re-derives from one of the allowlisted destination **descriptors** at some index ≤ `max_derivation_index` — comparison is scriptPubKey equality against the derived script, never string address comparison; same bounded re-derivation machinery as input ownership — or (b) is verified change. Anything else — including OP_RETURN, and an allowlisted wallet's address beyond the index bound — is refused. Descriptor entries (not fixed addresses) exist because policy is static: fixed addresses would force address reuse on the hot wallet forever. Setup requires at least two entries: hot wallet + escape cold wallet (see Wallet Topology). | v0 |
| Verified change | Output script re-derives from the node's own descriptor (either chain) at index ≤ `max_derivation_index`; the PSBT derivation path is an untrusted hint as above. An output merely *labeled* change is refused (eng review D6). | v0 |
| Fee cap | Fee (Σ inputs − Σ outputs) ≤ the fixed `MAX_FEE_PERCENT` (10%) × Σ inputs, all classes. A generous bug guard, not a security control: the Hold and the PIN carry the burn-attack defense, and a tight cap could refuse a panic-priced escape sweep (ADR-0006). | v0 |
| Hot budget | Hot-class outflow is bounded twice ([ADR-0014](adr/0014-hot-spend-bound.md)): **per transaction**, outflow ≤ `hot_max_per_tx` (`HOT_BUDGET_EXCEEDED`), checked in policy-core beside the allowlist and fee checks — pure, chain-view-free, federation-uniform; and **per window**, Σ of the hot outflow this node has *accepted* in the last `hot_window_secs` ≤ `hot_max_per_window` (`HOT_VELOCITY_EXCEEDED`), metered by a node-local reserve/release ledger. Outflow counts outputs to neither the vault nor the escape wallet — vault change, escape outputs, and the fee are all excluded (change and escape are not losses; the fee is already bounded by the fee cap and is not attacker-extractable). Escape and Refresh therefore never consume budget, as a consequence of the definition rather than a class test. All three params plus the hot/escape descriptors and `max_derivation_index` are pinned in the Manifest preimage, so a node whose budget policy differs from the sealed manifest fails startup — a cap is only as strong as the laxest classifier. All three are also config-validated at load: `hot_window_secs >= max_commitment_age_secs`, both caps non-zero, and `hot_max_per_tx <= hot_max_per_window` (a larger per-tx cap can never be reached, since the ledger reserves the whole outflow at ingress). Both checks run **before signing**. With `c < t` compromised signer Nodes able to bypass their ledgers, this bounds newly admitted completable outflow to `((n−c)/(t−c))·V` per window. For production `n = 2t−1`, the pure ADR-0012 censorship residual (`c = 0`) is `(2 − 1/t)·V < 2V`; the full `c = t−1` soft-vault tolerance is `tV`. | v0 |
| Hold | Every class is signed at ingress. A hot-class partial stays inside its node until `hold_secs` elapses, then the nodes may release, combine, and broadcast it; escape sweeps and refreshes release immediately. A refresh is submitted ONLY as the pin-less `RefreshRequest`, which signs under the ADR-0013 §6 bounds (`REFRESH_TOO_SOON`, `REFRESH_FEE_EXCEEDS_CAP`, `REFRESH_SUBORDINATED`); a refresh-class `SpendRequest` is refused `PSBT_INCONSISTENT`, which is what keeps refresh off the duress surface. The escape sweep is the implicit cancel of any pending spend (ADR-0004). | v0 |
| PIN | Every submission carries a PIN verified against the enrolled hashes: normal authorizes, duress triggers `duress_response` while answering identically (ADR-0008). No valid PIN → nothing is ever signed. | v0 |
| Sighash enforcement | The user's signature **cryptographically verifies against the node's own recomputed sighash** for the primary spend branch (presence of a `partial_sig` field is not enough), and all signatures MUST be SIGHASH_ALL (SIGHASH_DEFAULT under Taproot). This *subsumes* the old "no output mutation after authorization" check: with authorize+sign collapsed into one atomic step, any mutation after user signing invalidates the very signature the node verifies. | v0 |
| PSBT consistency | Global/input/output sections consistent and complete; undecodable input → 400 at the wire, decodable-but-inconsistent → `PSBT_INCONSISTENT` refusal. | v0 |
| Prevout ground truth | Input outpoints exist, are unspent, and match amount+script per the node's **own chain backend**. v0 trusts the PSBT's `witness_utxo` (regtest, honest coordinator); v1 must not (eng review D10). | v1 |

**Scope note**: spending delays are now IN — the Hold (ADR-0004) supersedes the earlier decision that deferred them. **Amount and velocity limits are now IN too** — the **Hot budget** ([ADR-0014](adr/0014-hot-spend-bound.md)) supersedes "velocity limits remain FUTURE work": a per-transaction cap `hot_max_per_tx` on hot-class outflow plus a rolling-window cap `hot_max_per_window` over `hot_window_secs`, enforced at ingress before signing. It landed exactly as the earlier note predicted it would have to — *static config*, sealed at setup and pinned in the Manifest preimage, evaluated per-node, **never dynamic policy and never gossip** (see locked decisions). The one refinement: the window is metered against each node's own ledger of the hot spends **it accepted** (pending + broadcast), not against its chain view, because a bound that counted only confirmed outflow would let an attacker queue several vault-sized spends into one Hold and have them all clear. Per-node rather than federation-aggregate metering costs a routing factor of `(n−c)/(t−c)` with `c < t` compromised signer Nodes: `n/t = 2 − 1/t < 2` when every signer enforces its ledger (`c = 0`), rising to `t` at the full `c = t−1` soft-vault boundary. That cost is what keeps "never gossip" intact.

**Evaluation contract (the purity boundary)**: policy-core is pure — `evaluate(psbt, policy_config, resolved_prevouts, now) -> Verdict` — same inputs, same verdict on every node; federation consistency depends on it. vault-node owns all I/O: it resolves prevouts through its chain backend and supplies the clock. The backend trait lives in vault-node, never in policy-core.

**Transaction commitment** (vault-proto's core struct — inlined here so the spec stands alone; adapted from IDEA.md §5.6): `wallet_id` (hash of the vault descriptor), all input outpoints, all output `(scriptPubKey, amount)` pairs, absolute fee, `expiry` (unix seconds, coordinator-proposed; a node refuses any expiry beyond `now + max_commitment_age_secs` by its **own** clock, so a hostile coordinator cannot inflate the replay log's retention), `policy_version` **[SUPERSEDED by [ADR-0012](adr/0012-model-b-spend-and-duress-architecture.md) + [ADR-0013](adr/0013-concrete-protocol-schemas.md) §2 — this field list is INCOMPLETE: the commitment MUST also bind the exact unsigned transaction's `version`, `nLockTime`, and every input's `nSequence`. ADR-0012 requires the commitment to bind the exact unsigned transaction so two distinct transactions never share a commitment id — otherwise the node-to-node channel could gather non-combinable partials]**. Serialization must round-trip byte-identically on coordinator and node (T4), but the encoding itself is greenfield until v1 — it may change freely between releases since both sides always ship from the same workspace.

**What the anti-replay log is — and is not** (re-derived after the authorize/sign collapse): with user-signs-first and SIGHASH_ALL, a node's signature is bound to the exact transaction, so resubmitting an identical PSBT yields the same signature on the same txid — harmless. The log does **not** defend the signature. It exists for three lesser jobs: (1) **idempotency** — an identical commitment resubmitted within its expiry returns the recorded verdict; (2) **audit** — every sign/refuse decision is on record for the incident-response loop; (3) **foundation** — velocity limits, if ever added, need exactly this record. The log is keyed by **commitment hash, never by outpoint set**: a replacement transaction (RBF fee bump, retry after failed broadcast) is a new commitment and gets a fresh policy evaluation — the log must never block legitimate replacement. v0 keeps the log in memory, pruned at expiry (eng review D9); a restarted node forgets in-flight commitments, which is acceptable because the log provides idempotency and audit, not signature security. The attack-scorecard claim "replay: refused" therefore means "an expired or tampered commitment is refused," not "the log is what stops replays." With the Hold (ADR-0004) the log gained a fourth job: it records each hot-class commitment's `first_seen` and pending status — the log IS the hold timer. Lockdown state is separate but, like all mutable node state, RAMDISK/node-lifetime — nothing survives a reboot because the entire deployment runs from tmpfs, and a rebooted node is DEAD (bare machine, full re-provisioning), which is strictly stronger than any persisted lockdown (ADR-0008 as amended by ADR-0007; reboot-death/tmpfs, 2026-07-16).

**Per-node chain backend** (eng review D10): the input-ownership and prevout amount/script checks require ground truth about the chain, not the numbers a coordinator puts in the PSBT. Each node validates against **its own** Bitcoin data source (Bitcoin Core, an Electrum server, or BIP158 compact block filters) so a lying coordinator can't feed forged prevout amounts through the fee/amount checks. This also reinforces real independence — nodes share no oracle. v0 (regtest, localhost, honest coordinator) may trust the PSBT's `witness_utxo` data; v1 must not. v0 ships the backend **trait seam** with a trust-the-PSBT implementation behind it, so the lying-coordinator refusal (T6) lands in v1 without touching policy-core. Note the trait must serve double duty: prevout resolution for policy checks AND the watchtower scan (ADR-0001). Backend choice (Core vs Electrum vs filters, and the privacy/availability tradeoffs each carries) is a Phase 2 decision. Authorization is bound to the exact unsigned-transaction commitment (struct defined in the Policy model section above), never to a coordinator-supplied summary.

User-first signing means a node's signature never exists on a transaction the user hasn't committed to, and each node's policy pass is bound to its own signature — there is no separate authorization artifact to steal or replay; the Hold inserts a visible waiting period, not a stealable token.

Decisions locked in eng review:

- **Mixed outcome (quorum reached, some node refused): proceed and broadcast, but every refusal emits a mandatory structured alert** naming the refusing node and reason. One wedged or hostile node can never freeze funds (that's what t-of-n buys), but a refusal is always surfaced as an incident — it means config drift or a partially caught attack, never noise. The compromised-node attack scenario demos exactly this. v0 alert artifact, concretely: a structured JSON event on the coordinator's stdout plus a scorecard field and distinct exit path in the demo output — greppable and testable (T5). A durable user-facing channel is Next Steps step 3 work.
- **Anti-replay log is bounded**: entries are pruned once their commitment expires (every commitment carries an expiry, capped by the node's own `max_commitment_age_secs`), so node state stays small; v0 keeps it in memory. What the log does and does not defend is spelled out in the Policy model section.
- **Key generation is on-node**: each vault-node derives its private key on its own host at provision time; only the public key travels back to the CLI, which assembles the descriptor from pubkeys. No machine ever holds two node keys — the t-of-n independence claim is true from key birth. MVP key handling: keys live **in memory only**, wskdf-derived at startup from an operator-held preimage (see locked decisions below) — nothing at rest on the node. **Implemented by `btc-vault setup` (2026-07-25, bead btc-policy-9y5.5); the procedure is `docs/SETUP-CEREMONY.md`.** Future option: encrypted key import, where a key is uploaded to a node encrypted against that node's ephemeral public key (restore/migration without plaintext transit).
- **Node API access control**: v0 nodes bind 127.0.0.1 only. v1 uses mTLS — the deployer mints per-node certificates at provision time and `/sign` requires a client cert — so policy probing and flooding die at the transport layer. v1 nodes are also exposed as Tor hidden services (NAT traversal + endpoint privacy; Tor client authorization can layer on top of mTLS).

Decisions locked in the open-questions pass (2026-07-13, user):

- **Script type: P2WSH now, Taproot later.** v0 and the first mainnet-capable release use `wsh()` (boring, best device support today); Taproot is a future migration, not a v1 blocker. With a fixed descriptor template the descriptor is hand-written — Liana's policy compiler is not needed, since spending policies never become user-configurable (next bullet).
- **Policy is static, permanently.** Once vault setup completes there is NO mechanism to change policy — not in v1, not later; dynamic policy is a declared non-goal for any reasonable future. This deletes what was the sharpest open edge (authenticating policy *changes*) by construction: an attacker holding the user key cannot edit the allowlist, because nobody can. Changing policy means provisioning a new vault and moving funds to it through the normal spend path (the rotate flow).
- **3-of-5 is the default federation** (demo and recommendation): it shows the federation properties properly — two nodes can be down or refusing and the vault still works, while theft needs three compromised hosts plus the user key. t and n remain config parameters.
- **No intra-node communication, ever.** Nodes never talk to each other; a node's only inputs are `/sign` requests and its own view of the blockchain. Any future stateful check (e.g., velocity) would be computed per-node from its own chain view — never from gossip. This collapses the former coordination-transport and shared-policy-state questions. **[AMENDED — nodes DO relay now (ADR-0012's channel: partials + duress carriers), but the policy-state half of this decision held exactly: the velocity check ADR-0014 shipped is computed per-node from that node's OWN ledger, and no node ever learns another's budget consumption. Paying under 2× in tightness to avoid velocity gossip was the deliberate trade.]**
- **Coordinator is trusted in the MVP.** The malicious-coordinator rules in this doc (D6 change re-derivation, D10 chain backend) define the *v1 hardening target*, not MVP requirements. The threat-model enumeration (T9) becomes v1 work.
- **Node keys are in-memory for the MVP, wskdf-derived.** No signing-key material at rest: each node derives its key at startup via wskdf (https://github.com/douglaz/wskdf — Argon2id, memory-hard, from a small operator-held preimage). A dead node **never rejoins the vault** — it holds no key at rest and the manifest is immutable, so a reboot ends that node permanently; restore capacity by rotating to a successor vault (reboot-death/tmpfs, 2026-07-16 — a reboot leaves a bare machine, ADR-0007). TPM/HSM hardening stays a post-MVP option. **SHIPPED 2026-07-25 (bead btc-policy-9y5.5)**, with one number corrected: the preimage takes wskdf's MAXIMUM WIDTH (63 bits), not the small recoverable width wskdf's own worked examples use, because recovery-by-brute-force is exactly what this deployment does not want — a lost preimage is a dead node, which reboot-death already makes routine. wskdf's generator pins the top bit of that 63-bit-wide value (an exact-width guarantee its recovery search needs), so the actual ENTROPY is 62 bits — a 2^62 search space, which is the most wskdf yields and stays infeasible under the memory-hard KDF. The startup derivation is therefore a ~1s Argon2id pass at the ceremony default (256 MiB, 4 passes) — also the enforced production floor — not the "~30s per pass" this bullet previously implied: the 2^62 preimage space is the primary barrier and the KDF cost is defence-in-depth on top. The per-node config carries only the public derivation parameters (`node_key_salt`, `node_key_ops`, `node_key_mem_kib`) and the preimage reaches the daemon on stdin; see [ADR-0013 §5](adr/0013-concrete-protocol-schemas.md) and `docs/SETUP-CEREMONY.md`.
- **Wire format is greenfield until v1.** vault-proto's encodings (including the commitment serialization) may change freely between releases; coordinator and nodes always ship from the same workspace, so no cross-version compatibility is promised before v1.
- **CTV/covenants are out of scope.** No covenant backend seam, no covenant-readiness requirement: this is a soft vault on today's consensus rules, full stop.

Decisions locked in the grilling pass (2026-07-14, user; full rationale in repo `docs/adr/0001`–`0009`, glossary in repo `CONTEXT.md`):

- **Nodes are the watchtower** (ADR-0001, **criterion revised by ADR-0012**): each node watches its own chain view for recovery-path spends and vault spends it never **validated and policy-accepted**. NOT "never co-signed" — in a t-of-n the n−t legitimate non-signers would false-alarm on every honest spend. See the corrected statement under *Mechanisms* below.
- **Coordinator pulls alerts/logs/liveness** (ADR-0002): nodes make no outbound connections; suppression/latency risk accepted. The coordinator also reconciles pulled sign-logs against its own history — a sign event it didn't originate means someone else is driving the vault.
- **Key-independence matrix** (ADR-0003): escape ⊥ user ⊥ recovery keys; CLI enforces best-effort (fingerprint tripwire), the setup ceremony carries the rest.
- **The Hold** (ADR-0004): nodes sign hot-class spends at ingress but keep their partials private for `hold_secs` (default 24h) before release, combination, and broadcast; escape sweeps and pin-less `RefreshRequest` self-spends release immediately, the latter under its ADR-0013 §6 bounds; the escape sweep is the implicit cancel.
- **Sealed nodes** (ADR-0005): post-setup, no SSH, no admin path, no upgrade-in-place; provider console + 2FA is the documented residual perimeter.
- **Fee cap is a bug guard** (ADR-0006): one fixed 10% cap (`MAX_FEE_PERCENT`) for all classes; the Hold and PIN carry the burn defense.
- **Reboot = node death** (ADR-0007): accepted for MVP; the entire deployment runs from tmpfs, so a reboot leaves a bare machine and recovery is full re-provisioning (reboot-death/tmpfs, 2026-07-16); 3-of-5 is the budget; coordinator polling doubles as liveness monitoring; `/unseal` REJECTED outright.
- **Duress PINs** (ADR-0008): a PIN on every spend (doubling as a second factor — a stolen user key alone can no longer get anything signed); two-transaction signing ceremony; `duress_response ∈ {lockdown, sweep_and_lockdown}` (default `sweep_and_lockdown`) chosen at creation; fraud-flavored refusals as cover story; lockdown has no reset on sealed nodes — the exit is the recovery path.
- **No correlation class reaches quorum** (ADR-0009): deployer-enforced; wizard preaches 5 sealed VPSes across ≥3 providers; the coordinator laptop must not itself become a correlation class (no saved provider-console sessions).
- **Recovery timelock (target state, gated on `btc-policy-wdu`)**: per-vault descriptor parameter, 180-day preached default; refresh nags at 120/150 days.
- **v0.1 walking skeleton killed**: one v0 core milestone on the real protocol, with an internal "first light" checkpoint; the demo ships once, with both acts.

## Wallet Topology

The complete system is four wallets/keysets plus four mechanisms (locked 2026-07-13, user):

| # | Component | Kind | Role |
|---|---|---|---|
| 1 | **Vault** | wallet, two spend paths | Primary storage. Path A (normal): user key + 3-of-5 federation, policy-checked. Path B (recovery): `older(~180d)` **[SUPERSEDED by ADR-0013 §1 — was shown as `~90d`; locked default is 180 days = BIP68 30375 in 512-sec units; ≫ and distinct from the ~90-day refresh cadence]** + 2-of-3 recovery keys — the **fallback exit**: taken for loss / inheritance / a stuck vault, and after a failed escape + terminal lockdown (ADR-0008). It is NOT the first-line answer to an *active* attack — that is the normal path + the escape sweep — but it IS how funds re-emerge once a locked-down vault is the only state left (the wrench and post-duress rows below both end here). |
| 2 | **Hot wallet** | allowlisted destination | Daily spending; the risk budget. Static policy means it can never be un-allowlisted: if its keys are compromised, stop sending to it and rotate the vault when convenient. |
| 3 | **Recovery keyset** | 2-of-3 cold keys | Not a funded wallet — an alternate spend path over the same coins. Distribute geographically/socially (e.g., owner, bank box, lawyer/heir): this doubles as the **inheritance mechanism**. |
| 4 | **Escape cold wallet** | allowlisted destination, **mandatory at setup** | Single-sig offline hardware, keys independent of everything else. The rotate/race destination. Exists *because* policy is static: the allowlist baked at setup is every place the vault can ever pay, so the incident destination must be in it from day one. |

Mechanisms:

- **Watchtower** (v0; ADR-0001/0002, **recognition criterion revised by [ADR-0012](adr/0012-model-b-spend-and-duress-architecture.md)**): every node, against its own chain view — alerts on (a) any recovery-path spend and (b) any vault UTXO spend it never **validated** (saw and policy-checked the request) — NOT "never co-signed", which false-alarms on the n−t nodes that legitimately don't sign each spend. The coordinator pulls alerts and additionally reconciles node sign-logs against its own spend history to catch spends it didn't initiate.
- **Coin refresh**: a self-spend resets a coin's relative timelock. It runs through the normal path, so it **requires the user's hardware key** — the CLI batches and prepares refresh PSBTs; the user signs on a ~90-day cadence. Full automation is impossible by construction; the cadence is a UX parameter, not an implementation detail.
- **Rotate flow**: normal-path sweep of everything to the escape wallet after a compromise signal (stolen user key, compromised node, recovery-key race). Funding a successor vault happens from the escape wallet at leisure. Pre-generating a successor-vault descriptor and allowlisting it directly is a possible v2 refinement; the MVP keeps the escape wallet as the single incident destination.
- **Descriptor backup**: the full vault descriptor (all pubkeys). Without it, even valid recovery keys cannot find or spend the coins. Public-ish data — back it up promiscuously (paper, every node, the coordinator, alongside each recovery key). Also powers watch-only wallets and the watchtower.

**Recovery triggers (exhaustive)** — unrefreshed UTXOs *arm* the recovery branch; only loss *triggers* it:

1. Lost user hardware key → stop refreshing, wait out the timelock, recovery-sweep.
2. Lost federation (3+ nodes permanently gone) → same.
3. Inheritance/incapacity → heirs assemble 2 of the 3 recovery keys and wait.
4. Post-duress lockdown (ADR-0008) → the federation has no reset on sealed nodes; once safe, funds re-emerge exclusively through the recovery path.

An *unauthorized* recovery-path spend (stolen recovery keys) is answered by the **normal** path — watchtower alert, then race the remaining coins to the escape wallet — never by recovery itself.

**Scenario → response matrix:**

| Scenario | Detected by | Response | Path |
|---|---|---|---|
| Stolen user key | nothing signs without a PIN; sweep attempts → refusal alerts; allowlisted attempts hang in the Hold as pending spends the user never made | escape sweep (cancels any pending spend), then rotate | normal |
| Stolen user key **+ hot-wallet keys** (composite) | the pending spend, during the Hold | escape sweep before the Hold elapses; if missed, loss bounded by the hot balance (the declared risk budget) | normal |
| Coercion / wrench attack | the user signals silently via the duress PIN — externally identical to compliance | `duress_response`: escape sweep and/or lockdown, presented as automated fraud prevention; funds re-emerge via the recovery path once safe | normal → recovery |
| ≤2 nodes compromised/wedged | mixed-outcome refusal alerts | rotate (a node key is baked into the descriptor, so replacing a node = new vault) | normal |
| User key + 3 nodes compromised | watchtower (theft succeeds) | loss — the accepted soft-vault boundary | — |
| Stolen recovery keys (≥2) | node watchtowers see the recovery-path spend | best-effort race of remaining coins to escape; the real defense is refresh discipline — refreshed coins were never exposed | normal |
| Lost user key | user | wait out timelock, recovery sweep | recovery |
| Lost federation (3+ dead — incl. accumulated reboot deaths, ADR-0007) | coordinator liveness polling | wait out timelock, recovery sweep (rotate earlier, at 1–2 dead) | recovery |
| Death/incapacity | heirs | same | recovery |
| Hot wallet compromised | user/wallet | stop paying it; rotate when convenient (allowlist is immutable) | normal |
| Coordinator lost (data only) | user | rebuild from descriptor backup; no funds at risk | — |
| Coordinator **auth-key** lost (ADR-0012) | user | normal path BRICKED — the pubkey is pinned in the immutable manifest, so every future request (spend, refresh, escape) is rejected; only exit is the recovery timelock. Needs a backup/rotation story. | recovery |

## Open Questions

- **Refresh batching and privacy**: the recovery hazard itself is now fully designed (relative timelock counts from each UTXO's confirmation; 180-day default; node watchtowers alert on recovery-path spends; refresh = instant-class self-spend the user signs on nag). What remains open is the refresh *strategy*: consolidate UTXOs per refresh (cheaper fees, worse privacy and larger single-coin exposure) versus refresh-in-place per coin (costlier, preserves the UTXO set). Decide at Next Steps step 2 with real fee data.
- **PIN transport hardening**: nodes receive PINs in plaintext for hash-comparison, so a compromised node learns them (ADR-0008 accepts this for MVP — a node minority can't use them). Revisit alongside v1 mTLS: per-node PIN salting or PAKE-style verification if it earns its complexity.
- **Hardware-key integration via cyberkrill**: integrate the user key through cyberkrill (https://github.com/douglaz/cyberkrill — Rust; PSBT signing, multisig descriptor support; devices: Coldcard, Trezor, Jade, Tapsigner/Satscard). Open sub-question: which of those devices can register/display the vault's full Miniscript descriptor versus blind-signing the PSBT — verify per device once the descriptor freezes. cyberkrill-core is also a candidate reference (or dependency, subject to the simplicity rule) for the node chain-backend abstraction — it already speaks Bitcoin Core RPC, Electrum, and Esplora.
- **Untrusted-coordinator hardening (v1)**: when the trusted-coordinator MVP assumption is lifted, write the coordinator threat-model enumeration (T9 — what a compromised coordinator can and cannot do: leak privacy, deny service, forge PSBTs, attempt replay, suppress alerts; D11's coordinator-side alerting is knowingly vulnerable to that last one, accepted) and enforce the D10 chain backend. Until then these are documented v1 targets, not MVP work.
