# A rebooted node is a dead node (MVP)

> **Banner RESOLVED (user, 2026-07-16): strict reboot-death PICKED — this ADR stands as written.** ADR-0012's earlier persistence branch (duress schedule + own escape partial on disk, "running-but-signing-keyless" daemon) is NOT adopted. Node state lives on RAMDISK; nothing survives reboot. A rebooted armed node contributes no partial; if ≥ t remain, the surviving armed set attempts the best-effort sweep at T, while a fire-time failure or fewer than t survivors yields lockdown-only → recovery. Safety holds (fewer sweeps, never theft). See ADR-0012's "Persistence & reboot" invariant (rewritten to match).

**Deployment invariant (user, 2026-07-16): the ENTIRE node deployment runs from tmpfs/ramdisk — OS-image-as-provisioned, application, config, and all runtime state.** A reboot therefore leaves a **bare machine with nothing installed** — no keys, no config, no attempt-budget, no Lockdown flag, no schedule. This is what makes "reboot = death" literally true and closes the reconciliation both models (2026-07-16 spec review) raised: because the signing key is **equally volatile** with every other piece of state, a provider-console attacker cannot reboot-to-reset the pin attempt-budget or Lockdown while retaining signing capability — the reboot destroys the key in the same stroke. **A dead node never rejoins the old vault.** Reprovisioning with the SAME key + SAME manifest would be exactly the `/unseal` resurrection this ADR rejects (it resets Lockdown/budget for a coerced operator); a NEW key isn't in the immutable manifest, so it cannot rejoin either. So node death is **permanent for that vault**: you either run with `n−1` nodes (3-of-5 absorbs two) or, to restore capacity, **rotate to a successor vault** (new manifest, move funds via the normal path) — the same rotation the coordinator-key and policy-change stories already use. "Re-provisioning" therefore means standing up a *successor vault*, never resurrecting a node into the existing one. The load-bearing rule is: **all mutable node state is RAMDISK/node-lifetime, and its durability equals the signing key's — which is zero.**

**STRENGTHENED 2026-07-25 (bead btc-policy-9y5.5): there is no key in the config at all any more.** The v0 code's `node_seckey` field is retired. The per-node config carries only the PUBLIC wskdf derivation parameters (`node_key_salt`, `node_key_ops`, `node_key_mem_kib`), and the signing key is derived in RAM at startup from an operator-held preimage read on **stdin** (ADR-0013 §5). The earlier parenthetical — "'key at rest in a config file' in v0 code means at rest *in tmpfs*, which is not persistence" — is therefore obsolete rather than wrong: the argument it made is no longer needed, because the config an attacker reads names a 63-bit-preimage Argon2id derivation instead of a key. Everything above still holds unchanged, and one step more strongly: a reboot leaves a bare machine that has neither the config nor any way to obtain the preimage, so re-provisioning with the SAME key is not merely rejected by policy — the material to do it does not exist on the machine.

Node keys exist only in memory on sealed hosts (ADR-0005), so any reboot — host maintenance, kernel panic, provider migration — permanently kills that node. The MVP accepts this rather than weakening either property: no key material at rest, no admin path back in. The 3-of-5 federation is the budget: two node deaths are absorbed; the vault must be rotated before a third.

## Considered Options

- **Key at rest, auto-decrypted at boot** — rejected: the disk image alone would yield the key to a provider-level or rescue-mode attacker.
- **`/unseal` endpoint** — **REJECTED (user, 2026-07-16; was "deferred, maybe later")**: a re-key path back into a sealed box reopens the exact attack this ADR closed, and it is only safe with a durable never-cleared lockdown flag — an at-rest artifact the RAMDISK/nothing-at-rest rule forbids (and an at-rest "duress was detected" leak besides). Node attrition + vault rotation is the accepted price; the two hard sub-rules recorded here (durable lockdown flag; no location holds t preimages) stay as the reasons it cannot be safely revived, not as a roadmap.

## Consequences

- The coordinator's node polling doubles as a liveness monitor: a node that stops answering is presumed dead, surfaced to the user, and counted against the federation budget.
- Rotation guidance: at one dead node, plan a rotation; at two, rotation is urgent (three alive = bare quorum, zero margin — one more reboot strands the normal path and forces the recovery path).
- Node uptime becomes a selection criterion for hosts; the deployer should prefer providers/plans with low forced-reboot rates.
