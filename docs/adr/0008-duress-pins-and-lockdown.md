# Duress PINs: every spend ceremony carries a silent panic path

> **The mechanism is consolidated into [ADR-0012](0012-model-b-spend-and-duress-architecture.md), which is the source of truth** for the duress state machine (arm → armed/silent-freeze → unconditional Lockdown + best-effort Firing), the node-assembled deterministic escape, and the corrected threat model. This ADR remains for the dual-PIN and lockdown rationale; where it says the coordinator assembles/distributes the escape, 0012 supersedes it. A post-wrench Coordinator can strip ladder rungs and re-sign or swap an escape-class spend/residual pair, while remaining unable to redirect funds or steal. Read 0012.


Every `/sign` submission requires a PIN. Two are enrolled at setup (hashes in each node's static config): the normal PIN authorizes the requested spend; the duress PIN triggers the vault's configured duress response. Entering either is externally identical, and the two must be deliberately distinct (never typo-neighbors — a false trigger costs a recovery ceremony under sealed nodes, ADR-0005).

Every vault→hot spend is a two-transaction ceremony: the user signs the hot transaction AND an escape-sweep variant on the hardware device, every time, as normalized routine — so under coercion, signing the escape transaction raises no suspicion. The PIN entered at submission decides which one the nodes act on.

The duress response is a per-vault, creation-time choice:

- `lockdown` — nodes sign nothing and refuse everything onward.
- `sweep_and_lockdown` (recommended default) — the escape sweep plus lockdown.

> **Retracted by [ADR-0012](0012-model-b-spend-and-duress-architecture.md) (and [ADR-0013](0013-concrete-protocol-schemas.md) §5).** This creation-time `duress_response` choice is retired: duress is a **single mandatory mechanism** — the escape is **mandatory in every SpendRequest**, Lockdown at `T` is unconditional, and the escape sweep is best-effort. The "lockdown-only" toggle no longer exists (and is absent from the authoritative node config, ADR-0013 §5), although any fire-time failure still produces the lockdown-only → Recovery outcome.

**Silent, deferred, sign-now/broadcast-later, node-distributed, no abort** (revised 2026-07-14, superseding the original "instant sweep + instant lockdown"):

- **Silent and deferred.** An observable countermeasure endangers a hostage, so duress ingress does NOTHING observable: it records the arm intent; the schedule for unconditional Lockdown plus a best-effort escape Firing job commits when the carrier reaches `t` holders. The response deadline `T` is anchored when this node consumes the coordinator nonce rather than when it arms (ADR-0013 §6; the clamp row is ADR-0012:66). The later anchor is FORBIDDEN, not merely unconventional: arming is the t-confirmation commit (ADR-0012:62) and a post-wrench coordinator can push it later by slow or selective delivery, so measuring `T` from it would silently stretch the hostage window past what the user was promised (`channel.rs:3573-3579`). From PIN entry until `T`, the nodes remain externally indistinguishable from normal operation, so nothing on-chain or in node responses reveals the pending response.
- **Nodes assemble and broadcast — not the coordinator.** The escape is not a special mechanism: it rides the same node assembly+broadcast path as every spend (ADR-0010/0011). Under the current ADR-0012 protocol the coordinator relays the full user-signed PSBTs, each node validates the provided escape and signs its own partial at ingress -- but NO partial leaves the node before that candidate's authorized fire event (ADR-0012:81), so no combine can happen before `T`; that release gate is exactly why a compromised `t-1` minority cannot assemble and broadcast the sweep early and break silence. At `T` the node enters Lockdown and spawns the best-effort Firing job, which does the combine then (ADR-0012:70, and ADR-0012:72 is why Lockdown does not block that in-flight combine). The coordinator cannot broadcast early because it never holds a broadcastable escape; SIGHASH_ALL prevents byte changes, and once the carrier arms, Lockdown is uncancellable. It can still DEFER it: Lockdown is unconditional as a DECISION, but `enter_lockdown` needs the one `/sign` lock and an unfair mutex lets a flood of fresh signed requests overtake it with no finite acquisition bound (THREAT-MODEL R11). Unpreventable is not the same as prompt. It can still choose among already-user-signed request roles and ladder rungs as described above. Signing is off-chain, so the window stays silent.
- **A coordinator compromised at entry has bounded request-selection power.** It can drop or selectively deliver, strip ladder rungs and re-sign, or swap an escape-class spend/residual pair. That can suppress or downgrade the sweep or choose which signed leg releases immediately — but never redirect funds, cause arbitrary bytes to be broadcast, or steal. Total denial keeps funds safe in the vault. Guaranteed delivery under a hostile coordinator is the v1 user↔node direct path.
- **No abort of the safety track.** Once armed, no key, PIN, or command cancels Lockdown. This removes the coercion lever entirely: the victim can truthfully say "I can't stop it, nobody can," which is the strongest answer under a wrench attack. A mis-entered duress PIN therefore irreversibly finishes the vault, while the best-effort sweep either moves funds to the escape wallet or leaves them frozen for Recovery.
- **The pin is un-substitutable because it is ephemeral.** No encryption or signature-binding is needed. Pins are held in RAM only and **never persisted or logged anywhere — coordinator or node** (not the sign log, the anti-replay log, an alert, or disk; at the node, hash-compared and immediately discarded). A coordinator is honest during normal operation, so it accumulates no pin history; a coordinator compromised *only at the duress moment* has never seen the normal pin and cannot swap it in. And the user always enters the *duress* pin under coercion, so the normal pin is never observed by an attacker. This "never log pins" property is load-bearing security, not hygiene — the day a request is logged "for debugging," substitution comes back.

Lockdown state persists for the node's lifetime on RAMDISK — never durable disk (reboot-death PICKED 2026-07-16: a rebooted node is keyless-dead, strictly stronger than Lockdown, so reboot survival is unnecessary; a durable flag would also be an at-rest "duress was detected here" artifact) — and, on sealed nodes, has no reset: the only exit is the recovery path (timelock + recovery keys), which is the point: coercion has nothing left to demand.

All post-duress refusals present as automated fraud prevention (`FRAUD_SUSPECTED: funds quarantined by policy`), never as "duress PIN used". The software is open source, so an attacker knows a duress PIN exists — but they can never verify which PIN they were given, and the fraud-lockdown framing means even the on-chain outcome doesn't prove deception. The user's story is "the system locked itself; I cannot override it."

## Consequences

- The PIN doubles as a second factor on every spend: a stolen user key alone can no longer get anything signed (closing most of the remaining stolen-key surface).
- Nodes see submitted PINs in plaintext (hash-compare); a compromised node learns the one pin used in the request it handled, and nothing more (pins are never logged). Accepted: a minority of nodes cannot act on that alone, and the PIN is defense-in-depth, not the primary control.
- The escape variant must be re-signed whenever the UTXO set changes; the full-balance line on the device screen is covered by the (true) story that the system mandates re-authorizing the security sweep on every spend.
- Depends on the node assembly+broadcast spine (ADR-0010/0011): the escape uses it, so duress can't be built until nodes assemble+broadcast. Lockdown itself is node-local and needs no channel. Two escape *timings* coexist for the same destination: duress = delayed + silent; manual rotate / watchtower race = instant (`duress_delay_secs`-independent).
- Lockdown fires at `T`, not at PIN entry, precisely to keep the pre-deadline window silent (an immediate Lockdown would reveal the trigger to an attacker who probes with another spend).
