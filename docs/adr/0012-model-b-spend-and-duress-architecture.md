# Model B: node-assembled spends + the duress architecture (consolidated)

Status: accepted 2026-07-15 (user design session). This ADR is the **authoritative, self-contained** spec for the Model-B spend path and the duress mechanism. It consolidates and supersedes the relevant parts of ADR-0008 (duress), ADR-0010 (coordinator relay), and ADR-0011 (node channel); those remain as decision records but this ADR is the source of truth. It also revises ADR-0001 (watchtower) and ADR-0002 (alert delivery) as noted, and reverses two earlier locked invariants ("coordinator trusted in MVP", "no intra-node communication, ever").

## Threat model (precise — everything below depends on it)

- **Coordinator: trusted until the wrench attack, untrusted from that moment.** It is honest during all normal operation and **never persists the pin** (RAM-only, discarded each spend). At the wrench it may turn fully hostile. Consequence: a coordinator compromised *at* the wrench has no pin history, and since the user always enters the *duress* pin under coercion, it never learns the normal pin — so it **cannot substitute the pin**. It can drop or selectively deliver requests, but see "duress propagation".
- **Silence model A:** the duress response must be silent against an *outside* attacker (controls the coordinator/laptop + the physical scene) who has compromised **no node**. A compromised quorum node *can* detect a duress event (it hash-compares the pin) — accepted: silence has a weaker threshold (1 node) than theft (t nodes). Designing silence against a node-owning attacker would require hiding the duress bit from nodes (threshold crypto) and is explicitly out of scope.
- **Soft-vault boundary unchanged:** user key + t compromised nodes = theft. Up to t−1 compromised nodes tolerated for theft.

## Architecture: full Model B

The coordinator is a **pure relay, always** — it operates the user key, composes candidate normal-spend transactions, relays `{exact single-signed tx, pin}` to the nodes, and pulls alerts. It **never** combines partial signatures, finalizes, or broadcasts. Each node validates independently, signs its partial, exchanges partials with peers over the node-to-node channel, assembles the complete tx, and broadcasts via its own chain backend. This is uniform for **every** spend, so the escape path is exercised by every normal spend (battle-tested, no special-case seam).

What this buys and its limit: a hostile (post-wrench) coordinator can **censor** (drop) and **selectively deliver**, but cannot forge/redirect signatures, cannot broadcast (it never holds a complete tx), and cannot control broadcast timing. It cannot get a coerced spend signed without delivering the duress-pin'd request, which makes nodes arm the escape instead — there is no move that yields funds. Total censorship (drop to all nodes) is an accepted residual (funds stay safe in the vault; closed in v1 by a direct user↔node path).

## Transactions and exact-byte identity

- **User signs first.** For a normal spend the coordinator composes the exact transaction (coin selection, fee ≤ 10%, change); the user reviews outputs+fee on-device and signs it under SIGHASH_ALL, producing a **single-signed** tx. The user signature **freezes the exact bytes** — the coordinator cannot alter a coin/fee/output afterward without invalidating it, and nodes verify it (V0-1) and reject tampering. Nodes then validate policy + prevouts (their own chain view) and add partials over the *identical* bytes, so partials combine.
- **The commitment binds the exact unsigned transaction** — including `version`, `nLockTime`, and every input `nSequence` (resolves the parked V0-2/V0-3 gap). Two distinct transactions must never share a commitment id, or the channel could gather non-combinable partials.
- **The request is coordinator-authenticated.** The coordinator has its own auth keypair (generated at setup, its pubkey pinned in the per-vault manifest alongside the node channel identities). Every request is `sign(coord_key, {pin, spend tx, escape tx, nonce, expiry})`, and nodes reject any request not validly coordinator-signed and fresh. This authenticates the relay in v0 (before v1 mTLS/Tor) and — crucially — **closes the one-compromised-node duress trigger**: a rogue node cannot manufacture or replay a duress request because it cannot produce the coordinator's signature over a fresh nonce, and peers reject an unsigned/stale propagated request. The coord key moves no funds (nodes still validate policy + user sigs independently), so it does not change the trust model. It does NOT close pin substitution: a *compromised* coordinator holds this key and signs whatever pin it chooses — that remains the Direction-3 residual.
- **The request is `{pin, spend tx, escape tx}` — all three mandatory, both txs user-signed.** A request missing the escape is invalid and rejected outright (so a hostile coordinator cannot "strip the escape" to force lockdown-only — it can only drop the whole request = total censorship, an accepted denial). The escape is composed like the spend (by the coordinator, over the current UTXO set at ceremony time), user-signed first (freezing its exact bytes), so it is **fresh** — built at the wrench, it covers deposits up to that moment.
- **Nodes validate the escape; they do NOT build it** (this dissolves the cross-node byte-identical-construction problem). Each node checks the provided, user-signed escape against policy — every input is a vault UTXO, every output pays the escape descriptor, the user signature verifies over the exact bytes (V0-1) — then adds its partial over the *provided* bytes. Same handling as the hot tx. The pin only selects which of the two candidate txs the nodes complete and broadcast (spend after the Hold; escape at T+delay + lockdown). There is **no stored standby escape**. Two node-side checks on the *provided* bytes (not construction — so cross-node determinism is unaffected) bound a *hostile-at-wrench* coordinator that composes a compliant-but-crippled escape (re-review #1): a **value-coverage threshold** (the escape must sweep at least X% — e.g. 95% — of the node's *own confirmed* vault balance) and a **feerate floor** (the escape's feerate ≥ a panic floor). Without these, a hostile coordinator could compose an escape over one dust UTXO, or over the full set at 1 sat/vB, so it "arms successfully" but strands the bulk of funds in the 180-day recovery limbo while the user believes it fired. Beyond the threshold, anything genuinely not covered (dust below the floor, a deposit arriving during the `[T, T+delay]` window) is a straggler left in the vault, recoverable via the timelock path. This kills both the dust-DoS (no stored-escape coverage check to fail) and the hostile-undercoverage attack.
- **Refreshes carry no pin — so they are not a duress surface** (this closes re-review #2 at its root, correcting an earlier over-fix). A refresh is a pin-less self-spend (vault → vault; nodes validate every output pays the vault descriptor, so it can move nothing to anyone and needs no pin). Because there is no duress-vs-normal decision on a refresh, it **cannot be coerced as a duress probe** — there is no signal to read. The `{pin, spend, escape}` request and the whole duress state machine apply only to **spends**. The one remaining instant-class *pin* ceremony is a deliberate escape-class spend (a rotate/incident action to the escape wallet — not routine); under duress on that rare ceremony the funds still go to the escape wallet, only deferred to T, so the *destination* is unchanged and the only observable is the delay — a minor residual on a rare ceremony, funds always safe.

## The node-to-node channel

- **Identity (ADR-0011 revised):** each node's channel key is **RAM-only, re-derived at startup** from the wskdf preimage (like the signing key; dies on reboot per ADR-0007 — no at-rest secret for a provider/rescue-mode attacker). Membership is an **immutable per-vault manifest**; each channel key is **endorsed at setup by that node's Bitcoin signing key** — the endorsement signs a domain-separated structure (`wallet_id, manifest_hash, node_id, channel_pubkey, protocol_version, transport_endpoints`) so it can't be replayed across vaults/roles — so peers accept a channel identity only if vouched for by a key already in the federation, and the **coordinator cannot mint or impersonate a node**. Peer authentication is **challenge-response** (a peer proves *possession* of the channel private key, not merely presents the public endorsement + pubkey — a replayed pair would otherwise impersonate).
- **Signing-oracle prohibition (absolute):** a peer message must **never** cause a node to create a signature. A node signs only after it has independently received and accepted the full user-authorized request (valid user sig, valid pin, exact tx, its own policy verdict, its own Hold/duress state). Peer claims ("I validated", "broadcast now") carry no authority. This is ordinary independent-ECDSA multisig — there is no legitimate nonce-exchange phase.
- **Message binding:** every partial envelope carries wallet_id, exact unsigned-txid, input index, signer node id, sighash type, spend purpose, protocol version, session nonce, and the user-signature hash it is bound to; peers verify each partial against the expected descriptor pubkey before storing/forwarding. Nodes keep their own canonical PSBT and import only verified signature fields (never blind-merge peer PSBTs).
- **DoS:** an authenticated-but-compromised minority can spam. Strict per-peer quotas, bounded message/session sizes, concurrency limits, deadlines, duplicate suppression, and isolation from the watchtower loop. No leader/single-assembler required for progress.
- **Transport:** v0 demo runs localhost (regtest); v1 exposes nodes as Tor hidden services with the endorsed-identity auth above.

## Duress state machine (per node)

1. **Idle (normal):** processes spends. No stored standby escape — every request carries its own fresh, user-signed escape.
2. **Arm** (a request whose pin matches `pin_duress_hash`, from the coordinator OR a peer): validate the request's user-signed escape against policy (user sig verifies, inputs are vault UTXOs, every output pays the escape descriptor, **value-coverage ≥ threshold of the node's own confirmed balance, feerate ≥ panic floor** — the #1 hostile-undercoverage guards); **propagate the full coordinator-signed duress request to all peers over the channel** so each peer independently verifies the coordinator signature + freshness, re-validates, and arms (one delivered node arms them all — kills selective/split delivery; safe against a rogue node forging a trigger because it cannot produce the coordinator's signature over a fresh nonce); compute `T = min(first_seen + duress_delay_secs, earliest pending hot-spend Hold-expiry − ε)` on the node's own clock — so the escape always fires *before* any frozen pending spend would have settled, closing the freeze-on-arm silence leak (nothing an attacker expects is missing before T; the escape's own on-chain appearance at T is the intended reveal); **assemble the complete escape immediately and persist the fully-assembled tx + T** to disk (not just the intent — so a reboot mid-assembly can't strand it); keep answering the coordinator normally (silent).
3. **Armed** (`[arm, T]`): silent to the coordinator/attacker; **silently refuses to finalize any hot-class spend** (stops a pending or coerced hot spend racing the escape); on reboot reloads the persisted complete escape and re-arms (broadcast needs no key — true only because the *complete* tx was persisted in step 2).
4. **Fire (at T):** broadcast the assembled escape via the chain backend and **re-broadcast the same bytes until confirmed** (fixed panic-fee, no re-signing); then enter Lockdown.
5. **Lockdown (terminal):** every request → `FRAUD_SUSPECTED`, persisted, no reset — exit is the recovery path only (ADR-0005). Presented as automated fraud prevention; the user's story is "the system locked itself, I can't override it."

`duress_delay_secs` is now purely the hostage-safety window (per-vault, `0` allowed). Per-node clocks fire within a small skew; redundant broadcast of the same tx dedups.

## Pin handling — Direction 3 (plaintext pin, accepted permanently)

Decision (2026-07-15, user): the pin stays a plaintext value entered into the coordinator and relayed to the nodes. A fully device-bound, coordinator-opaque duress token (Direction 1) would need hardware crypto beyond plain PSBT signing; a two-key device-visible scheme (Direction 2) closes substitution but sacrifices the hostage-safety window. Direction 3 is chosen because duress exists to protect the *person* (silence), the allowlist stops theft-to-attacker in every case, and the residual is honestly bounded.

Defenses (make Direction 3 as strong as it can be):
- **Ephemeral, never logged anywhere** (coordinator or node — not the sign log, anti-replay log, alerts, traces, metrics, crash dumps, or disk). RAM only; constant-time hash-compare; zeroize after use.
- **Trusted-until-wrench + never-persist** ⇒ a coordinator compromised *only at* the wrench has no pin history and can't substitute; the user always enters the duress pin under coercion, so the normal pin is never observed during the attack.
- **Node-side online-guessing defense (mandatory):** a persistent, federation-aware **attempt budget** with backoff/lockout — a post-wrench coordinator submitting guessed pins is bounded, not free to brute online, and guesses cannot be parallelized across nodes for free.
- **Higher-entropy pins are optional** (no longer load-bearing now that coordinator request-signing closes the one-node trigger): still nice against a compromised node offline-bruting the hashes to *detect* duress, but detection by a compromised node is already accepted under silence model A, so this is defense-in-depth, not required.
- **Coordinator host hardening:** run vault-cli on a dedicated, minimal, hardened host — **not the daily-driver laptop** — and ship it via **reproducible builds**. This is the primary mitigation for the accepted residual below.

**Accepted residual (SEVERE — see the reclassified list): a coordinator compromised *before* the wrench** (persistent malware, poisoned build, tampered dependency, or a wrench that begins mid-spend while the normal pin is still in RAM) can log/read the normal pin and substitute it, **silently nullifying the duress subsystem** — the escape never arms, no lockdown fires, and the user believes protection triggered. Funds are still not stolen to the attacker's address (the allowlist holds), but the panic path is dead and slow hot-wallet extraction is possible if the attacker also holds the hot keys. The host-hardening + reproducible-build mitigations shrink but do not eliminate this. Device-bound pin (Direction 1) remains the only true fix and is a hardware-gated future option, not planned for MVP.

## Watchtower under Model B (ADR-0001 revised)

**Recognition is by VALIDATION, not by signing.** In a t-of-n, every legitimate spend is signed by only t nodes, so the other n−t legitimately have no signature on it — "I didn't sign it" does NOT mean "unauthorized." A node therefore marks a vault spend "recognized" **iff it locally validated that request** (saw and policy-checked it), regardless of whether it ended up in the signing quorum — never merely because a peer asserted it. This requires the coordinator to fan **every** request to **all n** nodes (it already does — all n validate, only t sign). Then: a legitimate spend is validated by all n → recognized → no alert; a theft to a non-allowlisted address is one honest nodes would *refuse* on policy, so the attacker never sends it to them → they never validated it → they alert (correct). An offline/partitioned node that later sees an unrecognized spend still alerts.

**Code fix required:** V0-6 currently keys the "unrecognized spend" alert off the node's **co-signed** set — that is the wrong criterion (it false-alarms on the n−t legitimate non-signers) and must become the **validated-request** set.

**Recovery-path detection is separate and clean:** a recovery-branch spend is identifiable from the on-chain witness (which branch was taken), so it needs no "did I sign/validate it" reasoning — this is the most important watchtower job (stolen recovery keys are otherwise silent) and is unaffected by the above.

**Alert delivery** stays coordinator-pull (ADR-0002); per-node push is a *possible* v1 hardening, not committed — the coordinator is trusted pre-wrench (so recovery-key alerts deliver honestly), and during a wrench you already know you're under attack. The only gap is a simultaneous quorum+coordinator compromise (narrow).

## Accepted residuals (reclassified — none is theft-to-attacker, but not all are mere "degradation")

**Severe — nullifies duress or endangers the person (accepted, mitigated, honestly named):**
- **Pre-wrench-compromised coordinator substitutes the pin** (Direction 3 residual above) → duress silently nullified; user falsely believes it fired. Mitigated by host hardening + reproducible builds; true fix is Direction 1 (hardware-gated).
- **A compromised quorum node detects duress** → loss of *silence/physical safety* (silence model A's accepted boundary — one node, not t, breaks silence). And it does more than detect: it can hand the harvested normal pin to a hostile-at-wrench coordinator (which holds the auth key) to *nullify* duress — so one compromised node + a wrench that reaches the coordinator degrades to the pin-substitution residual above.
- **Hostile-at-wrench coordinator crippled escape** → bounded now by the value-coverage threshold + feerate floor, but the coordinator can still strand up to (100−threshold)% of the vault into recovery limbo. Denial/degradation, not theft.
- **Post-lockdown stragglers vs stolen recovery keys** → after lockdown the normal-path race is dead and refresh is impossible, so straggler coins sit exposed to a recovery-key holder for the ~180-day wait, with only a (coordinator-delivered) alert in opposition. Recovery-key custody is the sole protection in that window.

**Availability (funds safe, but the normal path or hostage window can be lost):**
- **Coordinator auth-key loss bricks the normal path** — the pubkey is pinned in the immutable manifest, so losing the key means every future request is rejected (normal path, refresh, escape all dead; only exit is the recovery timelock). Needs a backup/rotation story; DESIGN's "coordinator lost → rebuild from backup, no funds at risk" row is now FALSE and must be corrected.
- **Matured-pending collapses the hostage window** — if a hot spend's Hold already matured at arm, `T = earliest-expiry − ε` is in the past → the escape fires immediately (no silent window). So `duress_delay_secs` is a *ceiling*, not a guarantee; surface this in the ceremony UX.

**Denial / degradation (funds stay safe in the vault; recover via the normal or recovery path):**
- **Total coordinator censorship** (drops the duress request to all nodes) → nothing fires; funds safe. Closed in v1 by a direct user↔node path.
- **Sustained fee spike** above the escape fee → escape doesn't confirm → funds frozen → recovery path. (Note: interacts badly with the 10% fee cap on *small* vaults — see the escape-lifecycle work.)


## How this answers the three-model review (2026-07-15)

This ADR was itself re-reviewed by two models (2026-07-15) and NOT cleared on the first pass — several duress criticals survived and are being worked one at a time (see below). Progress log:

- **Resolved cleanly:** normal-spend exact-tx (user-signs-first freezes the bytes); "nodes build from intent" for the escape (nodes VALIDATE the provided user-signed escape, don't build it — dissolves the cross-node determinism critical); escape freshness/staleness + dust-DoS (fresh-at-wrench escape, mandatory in every request, no stored standby, lenient coverage → stragglers to recovery); reboot-mid-assembly (assemble the complete escape immediately on arm and persist the *complete* tx); split-lockdown (channel propagation); **one-compromised-node duress trigger (coordinator request-signing — a rogue node can't forge a coordinator-signed fresh request).**
- **Accepted (Direction 3):** pin substitution by a *pre-wrench-compromised* coordinator — nullifies duress, mitigated by host hardening + reproducible builds, not fully closed (device-bound pin is the hardware-gated true fix).
- **Also resolved:** freeze-on-arm silence leak (`T = min(delay, earliest pending Hold-expiry − ε)` — the escape fires before any frozen spend would settle).
- **Also resolved / decided:** watchtower recognition = validated-not-co-signed (fixes the n−t false-alarm; V0-6 code fix noted); alert delivery stays coordinator-pull, per-node push a *possible* v1 (not committed); escape keeps the 10% fee cap (a small vault in a fee spike falls to recovery — accepted).
- **Second re-review (2026-07-15) — 4/6 closed, NO theft path, structurally sound; two NEW fixable top-tier issues folded in this pass:** #1 hostile-at-wrench crippled-escape → node-side value-coverage threshold + feerate floor; #2 instant-class refresh duress-oracle → complete the refresh under duress + escape the post-refresh outpoints. Remaining spec-details to nail during V0-8 (not blockers): the coordinator auth-key lifecycle (loss bricks the normal path — needs backup/rotation, and DESIGN's "coordinator lost → rebuild from backup" row is now false); durable ARMING state + pin-never-persisted-in-the-envelope + response ordering; the partition/liveness behavior (armed minority < t can't fire — connectivity threshold or accepted severe residual); Armed→Lockdown on every failure branch (lockdown at T unconditionally, not only after confirm); the online-guessing budget as an actual protocol; and `T` edges (ε as a bounded margin; matured-pending ⇒ duress_delay is a ceiling not a guarantee). Then re-review before V0-8.
