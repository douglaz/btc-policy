# Model B: node-assembled spends + the duress architecture (consolidated)

Status: **LOCKED (design)** for V0-8; **V0-4 rides an implementation-semantics checklist** (2026-07-16). Seven adversarial review rounds — including two fresh-eyes whole-spec passes and a final gating re-review — by two independent models (gpt-5.6-sol + Fable 5). Final verdict, **both models agreeing**: the **two-track duress design is SOUND** — freeze+lockdown keyed on the duress pin alone (unconditional, chain-view-independent) closes the arm-split with **no route to vault funds**, and constant-observable ingress is **silent before T**. Fable: "no new theft path and no new silence break in the design itself; ADR-0012 can lock and V0-8 can start." The final round's two must-fixes are folded (the **Argon2 pin-compare timing** silence leak → compute both digests unconditionally; **V0-PLAN still directed the old arm-on-coverage model** → reconciled to arm-on-pin-alone). The residual protocol *semantics* (atomicity, idempotency, constant-time, fail-closed lockout, reboot) are captured as the **V0-4 implementation-semantics checklist** (below) — properties only code + the adversarial regtest harness can guarantee, not prose. Concrete wire/config/manifest schemas live in the companion [ADR-0013](0013-concrete-protocol-schemas.md). This ADR is the **authoritative, self-contained** spec for the Model-B spend path and the duress mechanism. It consolidates and supersedes the relevant parts of ADR-0008 (duress), ADR-0010 (coordinator relay), and ADR-0011 (node channel); those remain as decision records but this ADR is the source of truth. It also revises ADR-0001 (watchtower) and ADR-0002 (alert delivery) as noted, and reverses two earlier locked invariants ("coordinator trusted in MVP", "no intra-node communication, ever").

## Threat model (precise — everything below depends on it)

- **Coordinator: trusted until the wrench attack, untrusted from that moment.** It is honest during all normal operation and **never persists the pin** (RAM-only, discarded each spend). At the wrench it may turn fully hostile. Consequence: a coordinator compromised *at* the wrench has no pin history, and since the user always enters the *duress* pin under coercion, it never learns the normal pin — so it **cannot substitute the pin**. It can drop or selectively deliver requests, but see "duress propagation".
- **Silence model A:** the duress response must be silent against an *outside* attacker (controls the coordinator/laptop + the physical scene) who has compromised **no node**. A compromised quorum node *can* detect a duress event (it hash-compares the pin) — accepted: silence has a weaker threshold (1 node) than theft (t nodes). Designing silence against a node-owning attacker would require hiding the duress bit from nodes (threshold crypto) and is explicitly out of scope.
- **Soft-vault boundary unchanged:** user key + t compromised nodes = theft. Up to t−1 compromised nodes tolerated for theft.
- **Escape-key independence is load-bearing for the ENTIRE duress guarantee** (elevated from ADR-0003's best-effort tripwire per the fresh-eyes review). The duress escape sweeps the vault to the escape wallet; if the escape key is derivable from the user's seed, a post-wrench attacker who holds the user key **controls the escape wallet**, and the sweep hands them everything — a total, silent duress→theft conversion needing no node compromise. So this is a **hard assumption, not key hygiene**: the escape key MUST be generated independently, on-device, in a distinct setup-ceremony step (so the honest-lazy "one device exported both" case cannot occur), and the ceremony UX must state in bold that a shared-seed escape turns duress into theft. ADR-0003's fingerprint/xpub tripwire stays as defence-in-depth but cannot detect same-seed-with-stripped-origin, so it is not sufficient alone.

## Architecture: full Model B

The coordinator is a **pure relay, always** — it operates the user key, composes candidate normal-spend transactions, relays `{exact single-signed tx, pin}` to the nodes, and pulls alerts. It **never** combines partial signatures, finalizes, or broadcasts. Each node validates independently, signs its partial, exchanges partials with peers over the node-to-node channel, assembles the complete tx, and broadcasts via its own chain backend. This is uniform for **every** spend, so the escape path is exercised by every normal spend (battle-tested, no special-case seam).

What this buys and its limit: a hostile (post-wrench) coordinator can **censor** (drop) and **selectively deliver**, but cannot forge/redirect signatures, cannot itself broadcast (it never holds a complete tx), and cannot cause arbitrary bytes to be broadcast. It does hold the coordinator-auth key, so it can strip ladder rungs and re-sign or swap an escape-class spend/residual pair; that can suppress or downgrade the `T`-time sweep and choose which already-user-signed leg releases immediately (ADR-0016). It still cannot get a coerced hot spend released without delivering the duress-pin'd request, which makes nodes arm the escape instead — there is no move that yields funds TO THE ATTACKER — no new attacker-authorized spend can be produced. It does NOT mean nothing can move: an already-pending, user-authored hot spend can still finalize if the duress carrier fails to reach `t` and the coordinator censors. That is the accepted censorship residual, bounded by the Hot budget (ADR-0014). Total censorship (drop to all nodes) is an accepted residual: it stops NEW submissions, so nothing further can be authorized — but it does not make funds safe if a spend was already accepted before the wrench, because nodes fire that one on their own clocks at Hold expiry regardless of what the relay does afterwards. The bound is the same Hot budget. Closed in v1 by a direct user↔node path.

## Transactions and exact-byte identity

- **User signs first.** For a normal spend the coordinator composes the exact transaction (coin selection, fee ≤ 10%, change); the user reviews outputs+fee on-device and signs it under SIGHASH_ALL, producing a **single-signed** tx. The user signature **freezes the exact bytes** — the coordinator cannot alter a coin/fee/output afterward without invalidating it, and nodes verify it (V0-1) and reject tampering. Nodes then validate policy + prevouts (their own chain view) and add partials over the *identical* bytes, so partials combine.
- **The commitment binds the exact unsigned transaction** — including `version`, `nLockTime`, and every input `nSequence` (resolves the parked V0-2/V0-3 gap). Two distinct transactions must never share a commitment id, or the channel could gather non-combinable partials.
- **The request is coordinator-authenticated.** The coordinator has its own auth keypair (generated at setup, its pubkey pinned in the per-vault manifest alongside the node channel identities). Every SpendRequest binds `{spend tx, escape tx, escape_bumps, pin, nonce, expiry, policy_version}` under the coordinator signature, plus the vault's `wallet_id` domain separator; a RefreshRequest binds its corresponding pin-less fields. Nodes reject any request not validly coordinator-signed and fresh. This authenticates the relay in v0 (before v1 mTLS/Tor) and — crucially — **closes the one-compromised-node duress trigger**: a rogue node cannot manufacture or replay a duress request because it cannot produce the coordinator's signature over a fresh nonce, and peers reject an unsigned/stale propagated request. The coord key moves no funds (nodes still validate policy + user sigs independently), so it does not change the trust model. It does NOT close pin substitution: a *compromised* coordinator holds this key and signs whatever pin it chooses — that remains the Direction-3 residual.
- **The request is `{pin, spend tx, escape tx}` — all three mandatory, both txs user-signed.** A request missing the escape is invalid and rejected outright (so a hostile coordinator cannot "strip the escape" to force lockdown-only — it can only drop the whole request = total censorship, an accepted denial). The escape is composed like the spend (by the coordinator, over the current UTXO set at ceremony time), user-signed first (freezing its exact bytes), so it is **fresh** — built at the wrench, it covers deposits up to that moment.
- **Transaction class is DERIVED by the node from the spend's outputs — never trusted from a coordinator label** (fresh-eyes review; closes a new unprotected-duress-spend path). The channel envelope's `spend purpose` field is a hint, not authority. Normative predicate, on the *spend* tx: vault-change outputs are permitted in every class and excluded from classification; **escape-class iff every *destination* output pays the escape descriptor** (bounded index); **refresh-class iff every output pays the vault descriptor**; **hot-class iff every *destination* output pays a hot-allowlist descriptor**. **Mixed-class spends are rejected** (`PSBT_INCONSISTENT`-class refusal). Without this, an attacker sends 99%-to-hot + dust-to-escape and a naive "has an escape output ⇒ escape-class" rule would complete it *immediately* under the duress pin (escape-class completes now under either pin); with stolen hot keys that is extraction. Requiring every *destination* output to pay the escape descriptor for escape-class while allowing vault change alongside, and rejecting mixed destinations, removes the misclassification: a hot-heavy spend is hot-class, so under duress it is frozen and the escape sweep fires — the intended behavior.
- **Nodes validate the escape; they do NOT build it** (this dissolves the cross-node byte-identical-construction problem). Each node checks the provided, user-signed escape against policy — every input is a vault UTXO, every destination output pays the escape descriptor, every remaining output is verified vault change, and the user signature verifies over the exact bytes (V0-1) — then adds its partial over the *provided* bytes. Same handling as the hot tx. The pin only selects which of the two candidate txs the nodes complete and broadcast (spend after the Hold; escape at T, then lockdown). There is **no stored standby escape**. Two node-side checks on the *provided* bytes (not construction — so cross-node determinism is unaffected) bound a *hostile-at-wrench* coordinator that composes a compliant-but-crippled escape (re-review #1): a **value-coverage threshold** (the escape must sweep at least X% — e.g. 95% — of the node's own confirmed **+ vault-authorized-unconfirmed** balance; see build-over-mempool below), a **feerate floor** (the escape's feerate ≥ a panic floor), and **broadcastable-at-T**: (a) final `nLockTime` + non-relative-locking `nSequence`. For an escape with **no fee-bump ladder** that is `nSequence = 0xffffffff`, which makes E non-RBF-SIGNALLING. **That is a signalling choice, not a guarantee: under full-RBF — Bitcoin Core's default since v28 and widely deployed — a non-signalling transaction is still replaceable, so `nSequence` alone does NOT bar an RBF eviction.** What is left is a RACE, not a guarantee, and it should be read as one. No conflicting transaction can be authorized ANEW — those inputs require user + `t`, and arming freezes hot-class finalization — but a hot candidate over the same inputs that ALREADY reached its holder quorum and released partials before the arm is a complete transaction that peers may hold and relay, and under full-RBF it can replace the Escape if it meets replacement policy. The fire-time package-acceptance check keeps its original job — it is what stops the node broadcasting an escape the network will not accept, which is why it remains a fire-time sweep-admissibility gate and never an arm gate. What it does NOT do is settle this race: it tests the mempool as it is at fire, so it neither revokes an authorization already released nor stops a conflict relayed afterwards. What bounds this is not the escape's `nSequence` but the release gate plus the Hot budget: only a spend that already passed the gate can conflict, and ADR-0014 caps what it can carry. If it wins the race the sweep does not fire and only the vault-change remainder exits via Recovery. Characterise that honestly: if the conflicting spend pays the HOT wallet and the wrench attacker also holds those keys, its confirmation moves the Hot-budget amount to them. That is a BOUNDED VAULT DRAIN in ADR-0014's own words, not denial — the Hot budget limits the loss, it does not eliminate it. Denial is the outcome only when the conflicting spend pays somewhere the attacker does not control. Read non-signalling as reducing exposure on opt-in-RBF relays, never as an eviction bar. *(**REVISED 2026-07-26, bead btc-policy-9y5.7 — the fee-bump ladder.** A fixed panic fee is exactly wrong during a sustained fee spike, which is when the sweep most needs to confirm. A request may therefore carry `escape_bumps`: a bounded ladder of ADDITIONAL user-signed escape variants over the SAME inputs and the SAME output scripts, ascending by fee. It has to be user-signed material — the escape is SIGHASH_ALL over its exact bytes, so the federation holds no key that can raise its fee, which is also why CPFP is not available here: an anchor child would need either a federation-only key the vault does not have or an anyone-can-spend output large enough to pay the fee, i.e. a giveaway. For a LADDERED escape every rung, base included, carries `nSequence = 0xfffffffd` instead: BIP125-replaceable (rule 1) so a bump can actually replace the rung below it across a heterogeneous network, with bit 31 still set so BIP68 relative timelocks stay disabled. Finality then no longer comes from `nSequence`, so a laddered escape must additionally have `nLockTime == 0`, checked at ingress. Because only user+`t` can spend those inputs, replaceability grants a wrench attacker nothing: the highest rung anyone can assemble is still capped by the fire-time coverage guard.)*; (b) **every input is either confirmed OR the unconfirmed output of a *vault-authorized* transaction** (the vault's own spend-change or refresh — never an unconfirmed *external* deposit; see below); and (c) the **assembled package** (E plus any unconfirmed vault-authorized ancestors it chains off) passes the node backend's **full package-mempool-acceptance test** (e.g. `testmempoolaccept` on the package), not merely "relay-standard". **All three of these escape checks (coverage, feerate, package-acceptance) are FIRE-TIME sweep-admissibility checks under the two-track model — NEVER arm gates** (see the state-machine invariants; arming is keyed on the duress pin alone). They determine only whether the best-effort sweep fires; a failure leaves the node frozen + locked down → recovery.

  **Build over the mempool UTXO set, not confirmed-only (user, 2026-07-15 — corrects an earlier over-strict "confirmed inputs only" draft).** Unconfirmed vault UTXOs (spend-change, refreshes, and more) are the *common* case, so an escape restricted to confirmed inputs would strand real value in recovery limbo. The escape may spend a vault-authorized unconfirmed output because **it cannot be pulled out from under E**: replacing that parent requires a *conflicting* spend of vault UTXOs, which needs the normal path (user key + t-of-n node signatures) — a post-wrench attacker holds the user key but cannot obtain `t` node signatures for a conflict (the nodes committed to the parent, or are armed and refusing). Combined with "nodes never self-RBF" (the only broadcast behavior is re-broadcasting the *same* bytes) and "CPFP + package relay confirms a cheap parent," the parent is guaranteed to confirm, so E confirms. This is a stronger guarantee than any `nSequence`/BIP125 field, which is moot under Core's default full-RBF (opt-in signaling no longer prevents replacement). **Coverage (≥95%) is measured over confirmed + vault-authorized-unconfirmed value.** Two edges, both funds-safe: (i) **unconfirmed *external* deposits are excluded** from the mandatory-coverage set and never chained onto — their parents are *not* vault-authorized and can be replaced (a "toxic deposit" the attacker double-spends), so chaining onto one could poison E; a genuine deposit arriving at the wrench is a straggler swept by the next escape / recovered. (ii) **package/ancestor limits** (TRUC/mempool bounds on ancestor count+size) cap how many unconfirmed chains one escape can absorb — deep/numerous unconfirmed value may need a follow-up sweep; an implementation bound to measure in the V0-4 harness, not a design blocker. Without these, a hostile coordinator could compose an escape over one dust UTXO, or over the full set at 1 sat/vB, so it "arms successfully" but strands the bulk of funds in the 180-day recovery limbo while the user believes it fired. Beyond the threshold, anything genuinely not covered (dust below the floor, a deposit arriving at or after T) is a straggler left in the vault, recoverable via the timelock path. This kills both the dust-DoS (no stored-escape coverage check to fail) and the hostile-undercoverage attack.

  **Stage-1 composer narrowing (2026-08-23, `btc-policy-mby-spend-composer-l5p`).** The rule above and the node-side denominator remain unchanged. The first operator composer lands with a deliberately smaller capability: it composes only confirmed, mature, mempool-unspent vault coins. An opening/closing `gettxout(..., true)` null for a coin returned by the same-tip confirmed scan refuses the WHOLE command as **mempool-spent/unavailable** and tells the operator not to reissue until independent chain reconciliation; it is never silently omitted or diagnosed as merely “wait for confirmation.” The composer does not yet discover and include vault-authorized-unconfirmed descendants. Consequently the normal Spend command — and therefore its duress arm — is unavailable for as long as a prior vault spend remains mempool-spent. There is NO protocol time bound: a low-fee transaction can remain unconfirmed and mempool-resident indefinitely, and eviction does not prove the already-authorized transaction cannot be rebroadcast. Funds stay under the existing vault/Recovery authorities, but this is an unbounded availability loss and loss of the fast exit, not compliance with the general build-over-mempool rule. `btc-policy-w2b` must close before the release-candidate freeze (`btc-policy-gbw`); no production ceremony is authorized with this narrowing. That follow-up must add bounded authorized-unconfirmed discovery without admitting toxic external deposits or weakening the node denominator. The same release freeze is blocked by `btc-policy-yw4`: M3/M4 use finite Core, full-prevtx-memory and wire-envelope caps, so a confirmed external deposit from a pathological parent or sufficiently fragmented confirmed set can still force a loud Recovery-path denial until bounded protected-set selection/proof is designed.
  M3's one-change consolidation also leaves a one-UTXO vault after a normal Spend, while the incident escape-class pair requires two nonempty disjoint sets; `btc-policy-yw4` owns that reserve/output-topology decision too.
- **Refreshes carry no pin — so they are not a duress surface** (this closes re-review #2 at its root, correcting an earlier over-fix). A refresh is a pin-less self-spend (vault → vault; nodes validate every output pays the vault descriptor, so it can move nothing to anyone and needs no pin). Because there is no duress-vs-normal decision on a refresh, it **cannot be coerced as a duress probe** — there is no signal to read. The `{pin, spend, escape}` request and the whole duress state machine apply only to **spends** (a refresh is a distinct request type — see [ADR-0013](0013-concrete-protocol-schemas.md)).

  **But pin-less + instant means the refresh path has neither the Hold nor the pin that ADR-0006 relies on for its burn defense — so it needs its own bounds** (fresh-eyes review, user). Two node-enforced limits, both config: (1) a **minimum refresh interval** per coin (default ~1 month) — well under the ~90-day refresh cadence, so legitimate refreshes are unaffected, but a wrench-time coordinator can no longer drive *repeated* refreshes to burn the vault; and (2) a **tight refresh-specific fee cap** (a real self-spend pays a normal feerate — a small multiple of the node's fee estimate — never the 10% `max_fee_pct` that hot-class spends may use). Together these close the un-gated burn/extraction channel (ADR-0006's rationale — "the Hold and the pin carry the burn defense" — is false for refresh, so ADR-0006 is corrected). Refresh stays **pin-less** (a duress signal on the refresh path is unnecessary once burn is bounded, and re-adding a pin would reopen refresh as a duress surface). *(Precise scope: the min-interval bounds the burn RATE; it does NOT stop a key-holding adversary from keeping a coin's recovery branch perpetually immature — one refresh every < timelock suffices. That is denial-within-the-pre-wrench-SEVERE-residual, funds stay in-vault, and it stops the moment lockdown fires — recovery maturation against a key-holder rests on lockdown halting refreshes, not on the interval.)*

**Refreshes are subordinate to pending spends** (user, 2026-07-15 — closes the confirmation-review's post-arm-refresh-invalidation gap). While any normal-path spend is pending on the vault, a refresh is **queued behind it** (waits until the pending spend settles or is cancelled) rather than finalized. This is a *general ordering invariant*, active in all operation — not duress-specific — so it reveals nothing. It closes the gap because the **armed window always contains a pending spend**: the frozen hot spend that *triggered* the arm. So for the whole `[arm, T]` no refresh can confirm and spend the armed escape's inputs — `E` stays valid and fires at T. And it is **silent** where freezing refreshes (rejected option B) was not: the refresh is deferred for a reason the attacker *already sees* — their own visible pending spend — and behaves identically under both pins and in ordinary operation, so there is no armed-state signal. It also keeps the refresh path simple (no pin, no carried escape — none of the roll-forward machinery of the rejected option C). Three constraints on this rule, all confirmation-review results, are **load-bearing, not impl details**:
  - **The rule must be COARSE** — *any* pending spend blocks *all* refreshes, not just refreshes whose inputs overlap the pending spend. The armed escape sweeps ≥95% of the vault (many UTXOs) while the triggering hot spend touches a small subset; an input-overlap-granular rule would let a refresh spending an escape-input-that-is-not-a-triggering-spend-input finalize instantly and invalidate the escape. Only the coarse rule closes this.
  - **There must be NO pin-dependent cancel of a pending spend** (already true — ADR-0004 makes the escape the *implicit* cancel, with no explicit cancel protocol). A cancel op would be a duress oracle: cancel-then-refresh finalizes instantly under the normal pin (spend gone) but is held under duress (armed state keeps the triggering spend pending) — distinguishing the two. Preserve this as a standing constraint through V0-4.
  - **The escape-class duress branch is the exception to "the armed window always contains a pending spend"** — there the triggering escape-class spend *completed immediately* (it is not held), so subordination does not protect the residual escape there; closure in that branch rests on the immediate sweep having already moved the main funds, with the residual escape (disjoint inputs — see the escape-class coverage rule) covering stragglers. A refresh racing a straggler is still vault→vault and safe.
  Queue-vs-reject-with-retry remains a free impl detail (coarse queue is the default). Refreshes reset a 180-day timelock, so deferral behind a ≤24h Hold is immaterial; an attacker keeping a spend perpetually pending to block refreshes is bounded by commitment expiry and is denial-not-theft.* The one remaining instant-class *pin* ceremony is a deliberate escape-class spend (a rotate/incident action to the escape wallet — not routine). **It completes immediately under *either* pin** — the destination is the escape wallet either way, so there is nothing to defer and thus **no timing oracle** (closes re-review #3's escape-class-timing observable: a coerced escape-class probe settles identically under both pins). Under the duress pin it *additionally* schedules lockdown + a residual full-sweep at T (catching anything the escape-class spend didn't already move); under the normal pin it is just the plain escape-class spend. **Class-aware escape coverage (resolves the "residual sweep undefined" finding):** the escape tx in the `{pin, spend, escape}` request is always the user-signed, fresh residual — so no signature is conjured at T — but the coverage check depends on the spend's class: for a **hot-class** spend (frozen under duress) the escape *supersedes* it and includes the frozen spend's inputs, coverage = escape ≥ threshold of the confirmed balance; for an **escape-class** spend (which *completes*, so its inputs leave the vault) the escape must have inputs **disjoint** from the completed spend, and coverage is measured over their **union** (completed escape-class spend ∪ residual escape) ≥ threshold. Without the class split the escape-class residual is unsatisfiable — a full escape over the pre-spend set is invalidated the moment the escape-class spend confirms, and a residual over only the leftovers fails the flat 95% check. Funds always safe, and the only spend a normal PIN completes-now that a duress PIN defers-to-T is a *hot-class* spend — which is exactly the intended duress behavior.

## The node-to-node channel

- **Identity (ADR-0011 revised):** each node's channel key is **RAM-only, re-derived at startup** from the wskdf preimage (like the signing key; dies on reboot per ADR-0007 — no at-rest secret for a provider/rescue-mode attacker). Membership is an **immutable per-vault manifest**; each channel key is **endorsed at setup by that node's Bitcoin signing key** — the endorsement signs a domain-separated structure (`wallet_id, manifest_hash, node_id, channel_pubkey, protocol_version, transport_endpoints`) so it can't be replayed across vaults/roles — so peers accept a channel identity only if vouched for by a key already in the federation, and the **coordinator cannot mint or impersonate a node**. Peer authentication is **challenge-response** (a peer proves *possession* of the channel private key, not merely presents the public endorsement + pubkey — a replayed pair would otherwise impersonate). *(Concretized 2026-07-16, V0-8a eng review: possession is proven **per message** — every channel envelope is signed by the channel key over a fresh nonce + timestamp, replay-closed by a freshness window + seen-nonce set. The nonce+timestamp is the challenge; there is no session handshake and no connection state.)*
- **Signing-oracle prohibition (absolute):** a peer message must **never** cause a node to create a signature. A node signs only after it has independently received and accepted the full user-authorized request (valid user sig, valid pin, exact tx, its own policy verdict, its own Hold/duress state). Peer claims ("I validated", "broadcast now") carry no authority. This is ordinary independent-ECDSA multisig — there is no legitimate nonce-exchange phase.
- **Message binding:** every partial envelope carries wallet_id, **commitment_id** (the candidate key — the exact unsigned-txid alone collides across live commitments; ADR-0013 §4 / V0-8a registry), exact unsigned-txid, input index, signer node id, sighash type, spend purpose, protocol version, a **per-message nonce** (there is no session — the nonce+timestamp is the challenge; 2026-07-16), a **recipient node id** (so a valid envelope cannot be replayed to a different node even for a future directed message type), and the user-signature hash it is bound to; peers verify each partial against the expected descriptor pubkey before storing/forwarding. Nodes keep their own canonical PSBT and import only verified signature fields (never blind-merge peer PSBTs).
- **DoS:** an authenticated-but-compromised minority can spam. Strict per-peer quotas, bounded message sizes, concurrency limits, per-send deadlines, duplicate suppression, and isolation from the watchtower loop. No leader/single-assembler required for progress.
- **Transport:** v0 demo runs localhost (regtest); v1 exposes nodes as Tor hidden services with the endorsed-identity auth above.

## Duress state machine (per node) — normative

**Two independent tracks: SAFETY is unconditional and chain-view-independent; the SWEEP is best-effort.** A valid, coordinator-authenticated **duress-pin** request keys the **safety** track alone — freeze hot-class finalization + **lock down at T** — with **no** dependence on the node's balance, mempool, coverage, or fee judgment. Escape admissibility (coverage, feerate, `testmempoolaccept`) keys **only** the **sweep** track (whether the escape actually fires). This is the fix for the re-review's **arm-split conditional-theft** path: earlier, arming was gated on node-local *confirmed-set coverage*, which is **not** deterministic across backends (tip lag, reorg, propagation), so nodes could split — some arm and freeze the coerced hot spend, an unarmed sub-quorum does not, and at Hold-expiry the unarmed quorum signs it → theft if the attacker holds the hot keys. Keying the freeze+lockdown *verdict* on the **duress pin alone** removes the chain-view split. *(**REVISED 2026-07-19, V0-4b §0 — confirmation-gated arming.** The original text said "every node that receives the valid duress request freezes", i.e. each node arms locally the moment it sees a valid duress pin, then propagates. Implementation review found that ordering carries its own **arm-split theft class**: a post-wrench coordinator can make the carrier reach exactly one node and fail to reach the rest — corrupt the user-signed escape so local policy refuses before propagation, oversize the carrier past this or a peer's `max_msg_bytes`, or set an expiry that lapses mid-fan-out — leaving ONE frozen node and t−1 unfrozen ones, still a signing quorum for the coerced hot spend. Root cause: the local arm was decoupled from any guarantee that peers armed too. **The pin still decides the verdict, chain-view-independently; the COMMIT is now gated on evidence that ≥ t federation members hold the carrier.** A node propagates a request only after receiving and processing it, so receiving peer P's propagation of carrier C proves P holds C; a node counts ITSELF — once it has received, processed, and staged the carrier for fan-out — plus the distinct `sender_node_id`s that relay it back, and arms once that holder set reaches t, i.e. self + `t−1` peer receipts. Self-counting hangs off the STAGING path, not the signing path, which is what keeps a locked-out node's valid duress arm at self + `t−1` rather than silently demanding `t` other peers (invariant v, fail-closed lockout). Ingress records intent and propagates but never arms. If any honest node reaches t then t nodes hold C and, the fan-out being to all peers, they all reach it — so arming is all-or-nothing **in the limit**. Two qualifications belong with that claim rather than under it. It is EVENTUAL: fan-out is asynchronous and a peer relays only after processing, so nodes cross t at different instants and an early node can be armed while the remainder is still quorum-sized; that window is inherent to distributed arming (a commit barrier only moves it into an all-unarmed prefix, where the pending spend is equally unsuppressed) and what §0 rules out is the window never closing. And it assumes delivery is not partitionable per link: an adversary who can pass `t−1` peers' propagations to one node while blocking the links among the rest does obtain a genuine split, one armed node against `2t−2 ≥ t` unfrozen ones. That adversary is strictly stronger than ADR-0010's untrusted relay — the coordinator relays `/sign`, never `/channel` — and is out of model; sends retrying until the carrier's expiry mean it must sustain an exact link pattern for the carrier's whole life. This federation also requires exactly `n = 2t − 1` (ADR-0013 §1), which is what leaves no unfrozen signing quorum outside an armed set while still tolerating every `t−1` minority that withholds propagation. If the carrier cannot reach t nodes, NOBODY arms, which is the **censorship** residual already accepted below, not a split. **Constant-observable ingress (silence).** On EVERY request that passes the PIN-independent pre-PIN admission gates — normal or duress — a node performs the **identical operations in the identical order**: coordinator-auth + freshness; validate both the spend and (SpendRequest) the mandatory escape; write a **same-shaped schedule record in one atomic write to RAMDISK state** (a fire-time + a which-tx field — RAMDISK/node-lifetime, never durable disk, per tmpfs reboot-death ADR-0007: a literally durable schedule record would be the forbidden at-rest "duress was detected" artifact ADR-0008 bars); sign its own partial(s); propagate the request to all peers; then release a **fixed/size-padded response**. Coordinator/Carrier-capacity refusal is itself PIN-independent: it consumes no nonce, reads no pin, performs no memory-hard work, and does not propagate a request whose nonce it did not consume. The pin determines only the *contents* of the admitted request's schedule record — fire the spend at Hold-expiry, or fire the escape at T and lock down — never the *shape, timing, existence, or storage cost* of the work. A **normal** spend schedules its own fire through the *same* mechanism the escape uses, so there is **no** write, timer install, or lock acquisition that duress performs and normal does not — closing the storage-contention / queue-latency side channel. (Merely doing extra duress work *asynchronously after the response* does NOT close it — the re-review showed the attacker can keep concurrent probes in flight and measure the storage/scheduler disturbance; the work itself must be identical.)

**Confirmation-path silence — the `/channel` t-commit is ALSO a silence surface.** Under §0 the arm commits when a peer's propagation carries the holder set across `t` (the `/channel` receipt path), NOT at `/sign` ingress. That commit obeys the same constant-observable rule: a NORMAL and a DURESS carrier crossing `t` perform **identical store-lock work** — same candidate scan, safety-overlay write, selector allocations, delayed-window refresh — differing only in one internal selector bit. A NORMAL commit is **not a no-op**: it opens both candidates' release gate; only its overlay selector is inert. Therefore **any artifact derived from a holder-confirmation — a log line, counter, metric, timer, marker, response, or lock-contention profile — MUST key off pin-uniform state, NEVER the duress-only arm bit**, which differs exactly on a normal commit and would make the artifact present-under-duress / absent-under-normal (a duress oracle). Implementation contract (V0-4b+sxt): final confirmation produces either an idempotent `CarrierConfirmation { committed, armed }` or the pin-uniform actionable-clock retry. Production consumes `committed` for the harness-only `BTC_VAULT_CHANNEL_MARKER` and consumes the retry classification for the fixed response; retry eligibility keys only on `E`, `D`, active/staged state, `committed`, and the holder set, never the pin. `armed ⟹ committed`, and production never exposes `armed`. *(2026-07-22 holistic v0 audit: a silence oracle lived here — the `/channel` marker keyed on `armed`, firing only under duress — now fixed; this paragraph records the invariant so a future implementer does not reintroduce it by hanging an ordinary log/metric off the arm.)*

### Carrier ownership, clock authority, confirmation retries, and retirement

**Acceptance fixes lifetime once.** At the atomic coordinator-nonce acceptance transition for every channel-mode Spend request capable of owning a Carrier, the node computes accepted effective wall time `W`, process-monotonic instant `M` from that channel's production-fixed, test-pinnable `HotClock`, and signed expiry `E`; admission requires `E > W`, and checked arithmetic fixes immutable retirement deadline `D = M + (E - W)`. That accepted Spend nonce entry keeps `D` until the deadline lapses; there is no later release transition or second clock source. A wall clock already wrong at acceptance can make `D` too early or late and is an accepted residual. Later wall-clock changes, retries, relays, alternate signatures, Carrier retirement, and unrelated accepted requests never move it. The PIN-symmetry state projection records the pin-independent deadline under a test-pinned `HotClock`; it is not masked. A node built without channel mode has no Carrier or `HotClock`, so its accepted Spend nonces retain the existing wall-only lifetime.

**Post-acceptance wall clocks are attempt signals, not retirement authority.** Signed expiry `E` is the signed/federation-facing attempt-authority bound; `D` ends node-local logical residency and actionability. Physical intent/memo records may remain at or after `D` while an owner is ruling, but confer no holder authority. A new holder requires attempt time `< E` and `mono_now < D`. Raw wall time, `NonceLog::effective_now`, the fire sweep, handler re-reads, accepted-nonce pruning, and confirmation resampling cannot retire, replace, or extend an active or confirmation-pending Carrier while `mono_now < D`. Wall refusal retries only while `mono_now < D`; at/past `D` the outcome is terminal, opaque, and non-mutating. A fresh duplicate or already-completed confirmation remains an idempotent no-op; an outer-Stale already-held/completed case remains terminal `STALE_TIMESTAMP`.

**Exact actionable receipts retry.** At the memo lookup, post-KDF lookup, and final-confirmation clock-refusal sites, an authenticated wall-refused receipt returns fixed `RateLimited { retry_after_secs: 30 }` only while the resident nonce and signed expiry match, `mono_now < D`, the generation is active/ruling or staged, the holder decision is uncommitted, and the authenticated sender is not already counted. One second remains reserved for short owner-in-flight and nonblocking-KDF-busy states. The response mutates no nonce, capacity, holder, gate, commit, arm, candidate, eviction, or lifetime state.

**Outer-Stale is a receipt-only exception, never stale request admission.** After peer authentication and quota charging, an outer-stale `request` envelope may be bounded-zeroizing-decoded solely to recognize the exact resident Spend Carrier. Full coordinator-signature/body verification precedes identity lookup. Every stale outcome calls the same freshness diagnostic and consumes no envelope nonce. Diagnostic publication keys on `(peer, ingress freshness high-water)`: lower concurrent observations are discarded; an equal high-water updates a retained entry in place without changing its sequence and does not resurrect an evicted entry; only a strictly higher high-water may append. Final eligibility serializes briefly in the established `sign_state → store` order so it cannot observe the acceptance-to-Carrier-claim gap that q6v protects. Any alternate-signature KDF claim is made there, the memory-hard work runs outside both locks, and the result is revalidated after reacquisition. An exact live actionable receipt returns fixed `RateLimited { retry_after_secs: 30 }`; already-held, committed, horizon-ended, malformed, unknown, non-Spend, wrong-expiry/body, invalid-inner-signature, and other nonmatching cases remain terminal `STALE_TIMESTAMP`. Receiver wall-clock correction does not lower the channel's monotonic freshness high-water: under the current premise `coord_nonces.high_water < E`, a retry becomes fresh only after elapsed real time brings its timestamp back inside the 300-second past window, and only if both `E` and `D` remain live. Retries end at `E`/`D`; a larger excursion can make the authenticated channel unavailable for unbounded real time. `E`, `D`, capacity, the Hot budget, and Recovery bound retained state and loss consequences, not outage duration. The broader channel latch is `btc-policy-r1g`; the coordinator-nonce coupling is `btc-policy-coord-highwater-carrier-recovery-i3p`. The exception never enters ordinary `/sign`, reads the pin, or performs signing/candidate/outbox work.

**The body, not `coord_sig`, is Carrier identity.** Strict-DER/low-S ECDSA still permits a hostile coordinator to sign one body many ways. A fully verified exact signature tag is KDF-free. One unseen alternate signature may make at most one nonblocking Carrier-KDF attempt per sender and resident generation—including from the authenticated/quota-admitted outer-Stale receipt exception; busy consumes no sender claim and is retryable, equality records only the safe verified tag, mismatch spends the allowance, and a third unfamiliar signature is terminal while the exact resolved signature remains usable. Exact expiry, live horizon, uncommitted decision, and uncounted sender are preconditions; alternate resolution allocates no nonce/Carrier state and never restarts `D`. No fast digest, MAC, full signature, or request body that would let later process-memory capture cheaply test the plaintext PIN may be retained.

**One resident Carrier owns one coordinator nonce and one existing capacity slot.** Exact retries and alternate signatures resolve to it; a different body cannot create an overlapping generation while that nonce's replay/fan-out tombstone lives. Every accepted channel-mode Spend nonce carries `D`; NonceLog replay, live-entry count, and pruning treat it as resident while either signed wall expiry or `D` lives. Refresh and non-channel Spend keep ordinary wall-expiry behavior. An active or confirmation-pending Carrier owns its matching memo; every settled `Derived` memo names exactly one intent, while an active `InFlight` memo may precede intent creation. After early or completed Carrier retirement the nonce-only tombstone may legitimately outlive every memo. Refresh, non-channel Spend, and channel-mode Spend nonce tombstones share `MAX_COORD_NONCES`; there is no Carrier-specific cap, lease, counter, config, manifest field, refusal code, or protocol version. At capacity the node preserves all residents, consumes no newcomer nonce, does no PIN/KDF work, evicts nothing, and does not relay a request whose nonce it did not consume. Existing supersession/reinstallation guards remain defense in depth even where the resident-nonce rule makes them unreachable.

**Retirement is atomic and closed.** Carrier intent and memo retire together under the existing store lock only on: (1) a genuinely non-staged terminal owner exit, including poison-tolerant unwind; (2) completion of the full pin-uniform normal-release or duress-freeze holder-decision transaction, not an intermediate `committed` write; (3) `mono_now >= D` once no owner is ruling; or (4) reboot/process death. The store-locked prune pass may execute (3) wherever it is driven—the 1 Hz fire tick, `/sign`, or `/refresh`—using production-fixed `HotClock` monotonic time; its caller's raw/effective wall value has no Carrier-retirement authority. No cross-lock pin release exists: `D` simply lapses, and the replay/fan-out tombstone remains a capacity entry while either signed wall expiry or `D` lives. Ordinary nonce pruning removes it only after both have ended. Candidate/fire-window expiry remains independent. Capacity pressure, HTTP disconnect/timeout, staged refusal, receipt, replay, alternate signature, and raw/effective wall value are never Carrier-retirement authority.

## Pin handling — Direction 3 (plaintext pin, accepted permanently)

Decision (2026-07-15, user): the pin stays a plaintext value entered into the coordinator and relayed to the nodes. A fully device-bound, coordinator-opaque duress token (Direction 1) would need hardware crypto beyond plain PSBT signing; a two-key device-visible scheme (Direction 2) closes substitution but sacrifices the hostage-safety window. Direction 3 is chosen because duress exists to protect the *person* (silence), the allowlist **bounds** theft-to-attacker, and the residual is honestly bounded.

**CORRECTION (2026-07-30, codex + Fable spec review — the decision stands, one of its three reasons does not.)** The clause above read "the allowlist stops theft-to-attacker in **every case**". That is false, and this same ADR refutes it twice below: the residual paragraph concedes "slow hot-wallet extraction is possible if the attacker also holds the hot keys", and the reclassified list states it outright — *"A hot address whose keys the attacker controls is attacker-controlled even though it was allowlisted."* The allowlist constrains **where** coins may go, never **who controls the destination**, so it cannot stop theft in the case where the attacker owns an allowlisted wallet. What it actually does is force every outflow into a pre-committed destination set, which is what makes the Hot budget, the per-tx cap, the velocity ledger (ADR-0014) and the Hold enforceable at all — a real and load-bearing property, just a narrower one than "stops theft". Direction 3 survives on its other two reasons (silence protects the person; the residual is honestly bounded and now honestly attributed), and on the fact that Directions 1 and 2 remain unavailable for the stated reasons. **No decision changes here — only a reason that was overclaimed and is now stated at its true strength.**

Defenses (make Direction 3 as strong as it can be):
- **Ephemeral, never logged anywhere** (coordinator or node — not the sign log, anti-replay log, alerts, traces, metrics, crash dumps, or disk). RAM only; constant-time hash-compare; zeroize after use.
- **Trusted-until-wrench + never-persist** ⇒ a coordinator compromised *only at* the wrench has no pin history and can't substitute; the user always enters the duress pin under coercion, so the normal pin is never observed during the attack.
- **Node-side online-guessing defense (mandatory): a PER-NODE attempt budget** with backoff/lockout (decision, user — resolves the "federation-aware" wording that contradicted ADR-0011's no-shared-state). Each node independently rate-limits and locks out pin attempts against RAMDISK/node-lifetime state (see durability note below); no cross-node accounting (which would need shared mutable state the channel forbids). Per-node is sufficient because the pin is the *same* value at every node, so discovering it at one node reveals it for all — cross-node parallelization buys the attacker only a constant factor of `n`, which a strict per-node budget + lockout already bounds to uselessness. A post-wrench coordinator holding the auth key can sign fresh guess-requests, so this budget is what stops online brute-forcing of the normal pin; it must be an actual protocol (see [ADR-0013](0013-concrete-protocol-schemas.md): attempt count, window, backoff schedule, lockout state). **Durability = the signing key's durability, which under the tmpfs deployment (ADR-0007) is ZERO** (2026-07-16 spec-review reconciliation): the budget is RAMDISK/node-lifetime, and a reboot cannot launder it because the same reboot destroys the signing key and the whole installed system — a rebooted machine is bare, not a budget-reset signing node. The budget therefore does NOT need durable disk state (an earlier "persisted so a reboot cannot reset it" framing assumed keys survived reboot; they do not).
- **Higher-entropy pins are optional** (no longer load-bearing now that coordinator request-signing closes the one-node trigger): still nice against a compromised node offline-bruting the hashes to *detect* duress, but detection by a compromised node is already accepted under silence model A, so this is defense-in-depth, not required.
- **Coordinator host hardening:** run vault-cli on a dedicated, minimal, hardened host — **not the daily-driver laptop** — and ship it via **reproducible builds**.

  **CORRECTION (2026-07-30, codex + Fable spec review).** This bullet used to end "This is the primary mitigation for the accepted residual below," which credited one control with covering a threat it does not touch. The residual below names **four** vectors; map them one by one rather than averaging them into a summary sentence:

  | Vector | What actually addresses it |
  |---|---|
  | Poisoned build | **Reproducible builds** (`btc-policy-gbw`) — closed, given an independent rebuild on a different machine. |
  | Tampered dependency | **Reproducible builds** + dependency gates (`cargo audit`/`deny`; threat-model R4) — closed to the extent the dependency set is reviewed. |
  | Persistent/resident malware | **Host hardening only** (`btc-policy-4y3`), and only as *probability reduction*. Reproducible builds do **not** address this: resident malware needs no modified binary — an OS-level keylogger, a memory read, or a wrapper harvests the pin from a byte-identical `vault-cli`. The one narrow exception is **detection**: re-hashing the installed binary catches malware that persisted by patching it (the laziest strategy), and only if the check runs from *outside* the compromised host. |
  | Wrench beginning mid-spend, normal pin still in RAM | **Nothing.** No build property and no host configuration touches it. Ephemeral/zeroize handling (first bullet) shortens the window; it does not close it. |

  So: reproducible builds are **supply-chain provenance**, host hardening is **likelihood reduction**, and neither is prevention. The residual is **likelihood-reduced but unclosed** — not "mitigated". Its *severity* is unchanged and was already correct (top-listed SEVERE / CONDITIONAL THEFT in the reclassified list); what was wrong was the attribution, not the ranking. Consequence-bounding controls — the Hot budget and velocity ledger (ADR-0014), the Hold, the destination allowlist, and hardware user signing (`btc-policy-bq6`) — are what keep the loss finite once this vector fires, and they belong in the honest mitigation set alongside the two above. Direction 1 (device-bound, coordinator-opaque pin) remains the only true prevention, and is hardware-gated.

**Accepted residual (SEVERE — see the reclassified list): a coordinator compromised *before* the wrench** (persistent malware, poisoned build, tampered dependency, or a wrench that begins mid-spend while the normal pin is still in RAM) can log/read the normal pin and substitute it, **silently nullifying the duress subsystem** — the escape never arms, no lockdown fires, and the user believes protection triggered. Funds cannot be sent to an address outside the allowlist, but that is **not** the same as "not stolen": the panic path is dead, and slow hot-wallet extraction is possible if the attacker also holds the hot keys — an allowlisted destination they control is theirs, which is why the reclassified list below calls this CONDITIONAL THEFT rather than mere nullification. *(Wording corrected 2026-07-30: this sentence used to open "Funds are still not stolen to the attacker's address (the allowlist holds)", which contradicted its own second half.)* The host-hardening + reproducible-build controls **reduce the likelihood of two of the four vectors above and leave this unclosed** — see the vector-by-vector table under the hardening bullet; they do not shrink the mid-spend-wrench vector at all. Device-bound pin (Direction 1) remains the only true fix and is a hardware-gated future option, not planned for MVP.

## Watchtower under Model B (ADR-0001 revised)

**Recognition is by VALIDATION, not by signing.** In a t-of-n, every legitimate spend is signed by only t nodes, so the other n−t legitimately have no signature on it — "I didn't sign it" does NOT mean "unauthorized." A node therefore marks a vault spend "recognized" **iff it locally validated AND policy-ACCEPTED that request** (it authorized/would-authorize it — i.e. added its partial or would have), regardless of whether it ended up in the signing quorum — **never merely because it evaluated it, and never because a peer asserted it** (re-review fix: "saw and policy-checked" was too weak — a spend a node policy-*refused* was policy-checked but must NOT count as recognized, or a theft deliberately fanned to honest nodes would be marked recognized and suppress the alert). The node stores the **accepted/authorized** set, not every evaluated request. This requires the coordinator to fan **every** request to **all n** nodes (it already does — all n validate, only t sign). Then: a legitimate spend is accepted by all n → recognized → no alert; a theft to a non-allowlisted address is one honest nodes *refuse* on policy → not in their accepted set → they alert (correct), whether or not the attacker also fanned it to them. An offline/partitioned node that later sees an unrecognized spend still alerts.

**Code fix required:** V0-6 currently keys the "unrecognized spend" alert off the node's **co-signed** set — that is the wrong criterion (it false-alarms on the n−t legitimate non-signers) and must become the **validated-request** set.

**Recovery-path detection is separate and clean:** a recovery-branch spend is identifiable from the on-chain witness (which branch was taken), so it needs no "did I sign/validate it" reasoning — this is the most important watchtower job (stolen recovery keys are otherwise silent) and is unaffected by the above.

**Alert delivery** stays coordinator-pull (ADR-0002); per-node push is a *possible* v1 hardening, not committed — the coordinator is trusted pre-wrench (so recovery-key alerts deliver honestly), and during a wrench you already know you're under attack. The only gap is a simultaneous quorum+coordinator compromise (narrow).

## Accepted residuals (reclassified — most are denial, but two are CONDITIONAL theft, named honestly)

**Severe — nullifies duress or endangers the person (accepted, mitigated, honestly named):**
- **Pre-wrench-compromised coordinator substitutes the pin** (Direction 3 residual above) → duress silently nullified; user falsely believes it fired. **This is a CONDITIONAL THEFT path, not mere nullification** (fresh-eyes correction): the coerced vault→hot spend completes after the Hold, and if the attacker *also holds the hot keys* the funds are then theirs. A hot address whose keys the attacker controls is attacker-controlled even though it was allowlisted. **Likelihood-reduced but unclosed** by host hardening + reproducible builds — those cover the poisoned-build and tampered-dependency vectors and reduce the probability of resident malware, while nothing covers a wrench beginning mid-spend; see the vector table above *(wording corrected 2026-07-30: this read "Mitigated by")*. Bounded once it fires by the Hot budget/velocity ledger (ADR-0014) and the Hold; true fix is Direction 1 (hardware-gated). The same conditional-theft caveat applies to the escape-key-compromise assumption (threat model) — if the escape key is attacker-held, duress *is* theft.
- **A compromised quorum node detects duress** → loss of *silence/physical safety* (silence model A's accepted boundary — one node, not t, breaks silence). And it does more than detect: it can hand the harvested normal pin to a hostile-at-wrench coordinator (which holds the auth key) to *nullify* duress — so one compromised node + a wrench that reaches the coordinator degrades to the pin-substitution residual above.
- **Hostile-at-wrench coordinator crippled escape** → bounded now by the value-coverage threshold + feerate floor, but the coordinator can still strand up to (100−threshold)% of the vault into recovery limbo. Denial/degradation, not theft.
- **Post-lockdown stragglers vs stolen recovery keys** → after lockdown the normal-path race is dead and refresh is impossible, so straggler coins sit exposed to a recovery-key holder for the ~180-day wait, with only a (coordinator-delivered) alert in opposition. Recovery-key custody is the sole protection in that window.

**Availability (funds safe, but the normal path or hostage window can be lost):**
- **Coordinator auth-key loss bricks the normal path** — the pubkey is pinned in the immutable manifest, so losing the key means every future request is rejected (normal path, refresh, escape all dead; only exit is the recovery timelock). **Resolution (decision, user): rotation = a new vault** (the manifest is immutable, so a new auth key means a new manifest = a new vault), plus a **key-backup procedure** so ordinary loss is recoverable without a full rotation — the auth key is backed up like (but separately from) the descriptor backup; see [ADR-0013](0013-concrete-protocol-schemas.md). DESIGN's "coordinator lost → rebuild from backup, no funds at risk" row was FALSE and is corrected (data-loss vs auth-key-loss split).
- **Matured-pending collapses the hostage window** — if a hot spend's Hold already matured at arm, `T = earliest-expiry − ε` is in the past → the escape fires immediately (no silent window). So `duress_delay_secs` is a *ceiling*, not a guarantee; surface this in the ceremony UX.

**Denial / degradation (funds stay safe in the vault; recover via the normal or recovery path):**
- **In-flight refresh at the instant of arm — largely DISSOLVED by build-over-mempool** (user, 2026-07-15). The earlier concern (a refresh already broadcast before the duress spend arrives conflicts with an escape built over the *confirmed* set, and invalidates it) evaporates once the escape is built over the **mempool** set: it then spends the refresh's *output* (chaining) instead of conflicting over its input, and the refresh — a vault-authorized tx — cannot be replaced out from under it (a conflict needs t-of-n node sigs the post-wrench attacker lacks). The only remainder is the elaborate case where the attacker **pre-positioned** a second vault-authorized replacement of the parent (both signed pre-wrench) and broadcasts it post-wrench to displace the parent under full-RBF → the escape's chained input vanishes → escape doesn't fire. Still **denial, not a blocker**: the replacement is itself an allowlisted vault spend (funds stay vault/hot/escape-only), the coerced hot spend is dead (armed refusal + unconditional lockdown at T), so the outcome matches accepted total-censorship — funds safe, vault locks down, no theft, no silence oracle.
- **Total coordinator censorship** (drops/partitions the duress request so it reaches < the quorum) → the duress escape can't arm on those nodes. **Nuance (both final reviewers): "nothing fires, funds safe" is too strong when a hot spend is already PENDING.** Under Model-B sign-at-ingress a pending spend's partials already exist, so an un-suppressed quorum finalizes it at Hold-expiry. But that pending spend is **user-authored and user-destined** (to the user's own hot wallet, chosen before the wrench) — the attacker **cannot** manufacture a large attacker-destined normal-pin spend (they lack the ephemeral normal pin). So this reaches attacker funds **only** in the already-accepted composite residual (attacker also holds the hot-wallet keys), **bounded by the hot balance**, never the vault. Not a route to vault funds. For an admitted Carrier, freshness/lockout/partition variants are closed by fail-closed `Scheduled→Armed`, exact receipt retry, and node-to-node propagation. PIN-independent capacity refusal consumes, retains, signs, and relays nothing. Delivery-horizon refusal signs no partial and creates no Carrier intent/memo, but it retains the accepted nonce tombstone and the pin-uniform relay record. Neither contributes a coerced partial. Only true total-drop or sustained authenticated admission censorship leaves the bounded pending spend to finalize. Closed in v1 by a direct user↔node path.
- **Clock already wrong at Carrier acceptance** — the node fixes the process-monotonic retirement deadline from the signed lifetime remaining according to its accepted effective wall sample. Post-acceptance forward/rollback excursions cannot delete or extend Carrier state, but no local stopwatch can prove the admission sample itself was true. A bad sample can shorten or lengthen residency within the signed/max-age and existing coordinator-capacity bounds. The ordinary outcome is denial/degradation; if a too-short horizon leaves an earlier pending Hot spend unsuppressed while the attacker also holds `t−1` nodes and the Hot-wallet keys, it is the same Hot-budget-bounded CONDITIONAL THEFT composite named for total censorship above. Closing it needs external time authority or a protocol change and is not part of v0.
- **Sustained fee spike** above the escape fee → escape doesn't confirm → funds frozen → recovery path. (Note: interacts badly with the 10% fee cap on *small* vaults — see the escape-lifecycle work.)


## How this answers the three-model review (2026-07-15)

This ADR was hardened across four adversarial review rounds (2026-07-15); each round's criticals were resolved one at a time until the design converged to LOCKED (no theft, no silence break, denial-only residuals). Progress log:

- **Resolved cleanly:** normal-spend exact-tx (user-signs-first freezes the bytes); "nodes build from intent" for the escape (nodes VALIDATE the provided user-signed escape, don't build it — dissolves the cross-node determinism critical); escape freshness/staleness + dust-DoS (fresh-at-wrench escape, mandatory in every request, no stored standby, lenient coverage → stragglers to recovery); reboot-mid-assembly (originally resolved by persisting the *complete* escape tx on arm — **later REVERSED by reboot-death, ADR-0007 / the "Persistence & reboot" invariant above: nothing persists; a rebooted armed node is dead and the surviving armed set can still attempt the best-effort sweep**); split-lockdown (channel propagation); **one-compromised-node duress trigger (coordinator request-signing — a rogue node can't forge a coordinator-signed fresh request).**
- **Accepted (Direction 3):** pin substitution by a *pre-wrench-compromised* coordinator — nullifies duress, mitigated by host hardening + reproducible builds, not fully closed (device-bound pin is the hardware-gated true fix).
- **Also resolved:** freeze-on-arm silence leak (`T = min(delay, earliest pending Hold-expiry − ε)` — the escape fires before any frozen spend would settle).
- **Also resolved / decided:** watchtower recognition = validated-not-co-signed (fixes the n−t false-alarm; V0-6 code fix noted); alert delivery stays coordinator-pull, per-node push a *possible* v1 (not committed); escape keeps the 10% fee cap (a small vault in a fee spike falls to recovery — accepted).
- **Second re-review (2026-07-15) — 4/6 closed, NO theft path, structurally sound; two NEW fixable top-tier issues folded in this pass:** #1 hostile-at-wrench crippled-escape → node-side value-coverage threshold + feerate floor; #2 instant-class refresh duress-oracle → dissolved at the root (refreshes carry no pin, so there is no duress-vs-normal decision to read).
- **Confirmation review (2026-07-15, gpt-5.6-sol) — #1 closed narrowly (coverage+feerate), tx-graph sound; three items, two folded in this pass, one open:**
  - **FOLDED — broadcastable-at-T:** coverage+feerate alone let a hostile coordinator supply a fully-covered high-fee escape with a future `nLockTime`/relative `nSequence` that passes every check but can't be mined at T. Added a third node-side check: the escape must be **final + non-relative-sequence + relay-standard** (see the escape-validation paragraph).
  - **FOLDED — escape-class timing oracle:** a coerced escape-class spend settled immediately under the normal pin but was deferred under duress → readable. Now it **completes immediately under either pin** (destination is the escape wallet either way; duress additionally schedules lockdown + residual sweep at T). No timing observable.
  - **RESOLVED — post-arm refresh invalidation** (user, 2026-07-15): **refreshes are subordinate to pending spends** — while any normal-path spend is pending, a refresh queues behind it. The armed window always contains a pending spend (the frozen triggering hot spend), so no refresh can spend the armed escape's inputs during `[arm, T]`. Silent (the block is explained by the attacker's own visible pending spend, identical under both pins and in normal operation — unlike the rejected option B freeze, which was observable because refreshes are instant-class), and keeps refreshes simple (no pin, no carried escape — unlike the rejected option C roll-forward). See the refresh paragraph.
- **Verification round (2026-07-15) — two-model panel on the three confirmation-review fixes + the new subordination rule: codex/gpt-5.6-sol "blockers: yes (4)", Fable 5 "blockers: none (5 refinements)".** The divergence *was* the result — same attacks, split on classification. Reconciled and all folded in this pass:
  - **One true silence break → FIXED: dynamic T.** A post-arm second hot spend with a nearer Hold-expiry would settle-visibly under the normal pin but be frozen under duress, leaking armed state before T. Fix: `T ← min(T, spend Hold-expiry − ε)` on every hot spend accepted after arm (generalizes the freeze-on-arm fix beyond arm-time-pending). This was the only finding that broke a *safety/silence* property.
  - **Three spec-tightenings both models wanted → FOLDED:** (1) explicit **escape-inputs-confirmed + full-mempool-acceptance at arm** gate (closes the toxic-parent / unconfirmed-ancestor escape-invalidation); (2) **coarse refresh rule pinned** as load-bearing (input-overlap granularity reopens the disjoint-refresh invalidation); (3) **class-aware escape coverage** (hot: escape supersedes the frozen spend; escape-class: escape disjoint from the completed spend, coverage over the union) — makes the escape-class residual satisfiable.
  - **One dissolved:** the cancellation attack assumed a cancel op; ADR-0004 has none (escape is the implicit cancel). Recorded **no-pin-dependent-cancel** as a standing V0-4 constraint (a cancel op would be a duress oracle).
  - **One accepted denial residual (Fable's classification, adopted):** in-flight-refresh-at-arm escape-invalidation → funds safe in-vault + lockdown, identical to accepted total-censorship; not theft, not silence. Documented in the residuals list with an optional v1 close.

- **Post-lock refinement (2026-07-15, user) — build-over-mempool corrects the "confirmed inputs only" over-fix.** The confirmed-inputs gate above was too strict: unconfirmed vault UTXOs (spend-change, refreshes, deposits) are the common case, and confirmed-only strands them in recovery limbo. Corrected rule: the escape spends confirmed **or vault-authorized-unconfirmed** outputs, validated as a package at arm. Safe because a vault-authorized parent cannot be replaced without t-of-n node sigs the post-wrench attacker lacks (a stronger guarantee than `nSequence`, which is moot under Core default full-RBF) + nodes never self-RBF + CPFP/package-relay confirms cheap parents. This **dissolves the in-flight-refresh residual** (the escape now chains off the refresh's output instead of conflicting with its input).
